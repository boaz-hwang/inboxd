# 05 — Architecture Review (2026-09-16)

검토 대상: `docs/01–04` @ `2445081`. 검토 당시 main tree에는 제품 코드가 없었으므로
03-proposal의 설계를 검토했다.
원칙: 억지 개선점을 만들지 않는다. 문제가 없는 부분은 그렇다고 적는다.

## 결론

설계의 뼈대(로컬 인덱스 = 읽기 진실원인, coverage 동봉, outbox 경유 쓰기, OOB 승인,
Gateway core+ext, wrapper-first, fixture-first 한국어 검색)는 **건드릴 이유가 없다.**
흔한 함정(unknown≠0, 원자 트랜잭션, Uncertain 재전송 금지, 승인 바인딩)은
이미 설계 원칙에 반영되어 있다. 구현에서 지켜지는지는 아직 검증할 수 없다.

보완할 내용은 실행 주체, coverage 표현, 승인 접근 경계, 암호화 검증,
이벤트 적용 순서, outbox 실행 계약이다. 모두 구현 전 설계 공백 또는 검증 과제이며,
발생이 확인된 버그는 아니다. 해당 기능을 구현할 때 계약을 구체화하면 되고,
모든 결정을 끝내기 전까지 읽기 스파이크를 막을 이유는 없다.

## 개선점

### 1. 프로세스 토폴로지가 정의되지 않았다

문서에 **어느 프로세스가 무엇을 소유하는지**가 없다.
"TUI/MCP/CLI는 인터페이스일 뿐"이라고만 되어 있다. 이 결정은 아래 4가지를 한꺼번에 좌우한다.

- **쓰기 조정.** sync(백필·WS watch), MCP propose(outbox insert), CLI approve가
  동시에 실행될 때 쓰기를 어디서 조정하는지 정해야 한다. 여러 프로세스가 DB를
  연다는 사실만으로 결함은 아니며, 충돌 시 대기·재시도와 트랜잭션 경계가 필요하다.
- **watch 수명.** WS 구독이 TUI 켜진 동안만 살면 "최신성"이 TUI 사용 습관에 종속된다.
  오래된 coverage를 정직하게 표시하는 것과 원하는 최신성을 달성하는 것은 별개다.
- **OOB 승인 전달.** CLI에서 승인 대상을 조회할지, 상주 프로세스나 외부 서비스가
  알림을 보낼지 정해야 한다. OOB 승인 자체가 로컬 데몬을 필수로 요구하지는 않는다.
- **Uncertain 판정.** "프로세스 사망 시 자동 재전송 금지"는 누가 사망을 관측하고 receipt를
  `Uncertain`으로 확정하는지가 정해져야 실행 가능하다.

**제안.** 03-proposal에 "런타임 모델" 절을 하나 추가하고 둘 중 하나를 고른다.

| 모델 | 장점 | 비용 |
|---|---|---|
| (a) 데몬 1개가 DB write·sync·outbox 실행을 독점, 인터페이스는 로컬 소켓/HTTP 클라이언트 | writer 1개, watch 상시, 알림·Uncertain 관측 주체 명확 | 데몬 생명주기 관리, IPC 정의 |
| (b) 라이브러리 + 각 인터페이스가 임베드, DB 트랜잭션·필요한 실행 잠금으로 조정 | 설치 단순 | sync 실행 방법과 중복 실행 방지, 재시작 복구를 별도로 정의해야 함 |

상시 동기화와 여러 인터페이스의 동시 사용을 목표로 한다면 (a)를 우선 검토할 만하다.
다만 이름만으로 데몬을 확정하지 않는다. sync·outbox 실행 주체를 연결하기 전에
수명·접근 권한·재시작 책임을 정하면 된다. 데몬을 고르는 것만으로 승인 경계나
중복 발송 방지가 해결되지는 않는다(3·6번).

### 2. `sync_coverage`의 구간 표현 규칙이 명시되지 않았다

계약은 "수집 범위 = 백필 구간 + **중간 누락**"이라고 쓰여 있는데, 스키마는
`{platform, account, chat_id, from_ts, to_ts, complete, last_verified_at, limits}`다.
키와 채팅당 행 수가 없어 **한 행으로 제한된다고 단정할 수는 없다.** 다만 채팅당
한 구간으로 구현하면 다음 상태의 누락 위치를 표현하지 못한다.

- 최근 구간은 WS로 받고 과거는 백필 중이라 가운데가 빈 상태
- WS 끊김 후 재연결까지의 구멍
- 레이트리밋으로 특정 페이지만 실패한 상태

이 상태에서 `complete=false` 하나로 뭉개면 응답의 coverage는 "불완전"이라고만 말하고
**어디가 비었는지**는 말하지 못한다. 그러면 "결과 없음 vs 모름" 구분이 채팅 단위에서만
가능하고 기간 단위에서는 불가능해진다.

**제안.** 채팅당 여러 구간을 저장할 수 있음을 명시한다. 기존 필드로도 가능하며,
`complete`를 없애거나 스키마를 교체할 필요는 없다. 예를 들면:

```text
sync_coverage { platform, account, chat_id, from_ts, to_ts,
                complete, last_verified_at, limits }
  -- 채팅당 여러 행. 구간 경계와 중복 구간의 해석을 정의한다.
  -- 인접 구간도 최신성·제한 사유가 다르면 무조건 병합하지 않는다.
```

응답은 검색 기간과 교차해 `covered`와 `gaps`를 계산하되, 기존 계약의 검색 대상,
최신성, 제한 사유를 함께 유지한다. 관측한 메시지의 최소·최대 시각만으로 그 사이가
완전하다고 판정하지 않는다. 수집된 메시지가 없는 구간도 검증된 빈 구간과 미수집
구간을 구분해야 한다. 과거 수집 완료와 이후 수정·삭제 확인의 최신성도 구분한다.

**검증:** 가운데가 빈 두 수집 구간, 검증된 빈 구간, 수집한 적 없는 채팅,
백필 중단·재개에서 검색 기간별 coverage와 제한 사유가 유지되는지 확인한다.

### 3. 승인 경계는 DB 파일 수보다 접근 권한으로 정의해야 한다

아키텍처 그림의 store 목록에 `outbox`가 인덱스 테이블들과 나란히 있고, 패키지는
`index`와 `safety`로 나뉘어 있다. audit log의 저장 위치는 명시되어 있지 않다.
이 그림만으로 보안 결함을 확정할 수는 없다.

문제가 되는 조건은 위협 등급 (b)의 에이전트가 승인 저장소를 수정할 수 있고,
발송자가 행의 존재만으로 승인을 인정하는 경우다. 검색은 MCP/CLI/API로 제공할 수
있으므로 에이전트가 인덱스 DB를 직접 열어야 할 이유는 없다. 반대로 파일을 둘로
나눠도 에이전트가 둘 다 수정하거나 발송 토큰을 읽을 수 있으면 경계가 생기지 않는다.

wrapper-first도 같은 문제를 키운다. 감싼 CLI에 자체 send 명령이 있으면 "직접 send 경로를
코드에 안 남긴다"는 inboxd 코드 안에서만 참일 수 있다. 에이전트가 그 CLI와 발송
자격증명에 접근할 수 있는지까지 승인 우회 테스트의 범위에 포함하거나,
지원하지 않는 위협으로 명시해야 한다.

**제안.** 기존 로드맵의 승인 채널 설계에서 다음을 구체화한다.

- 에이전트・승인자・발송자별로 DB, 승인 채널, 발송 토큰, audit 기록에 대한 접근
  권한을 정한다. 셸 접근 에이전트까지 막겠다면 OS 권한 또는 샌드박스 등 실제
  접근 분리가 필요하다. 이를 구현하지 않는 MVP는 그 보호 수준을 주장하지 않는다.
- 별도 DB는 권한 분리에 필요한 경우 선택한다. 보호된 실행자가 단일 DB를 소유하고
  제한된 API만 노출하는 구성도 가능하다. 패키지와 DB 파일 수를 일치시킬 의무는 없다.
- 승인자 인증과 승인 내용 바인딩을 발송자가 검증한다. HMAC을 택하더라도 code만
  인증하는 것으로는 부족하다. intent ID·계정·채팅·답장대상·정확 본문·만료를 묶고
  재사용을 차단해야 한다. 에이전트가 승인 발급 API나 비밀에 접근할 수 있으면
  HMAC도 우회를 막지 못하므로, 현 단계에서 특정 암호 방식부터 확정하지 않는다.
- 승인 위조·재사용과 wrapper 직접 발송을 선택한 위협 등급에 맞게 검증한다.

### 4. "SQLite 암호화"가 Bun에서 되는지 검증되지 않았다 (Spike 0)

암호화 저장은 MVP 완료 조건("선택이 아니라 완료 조건")인데, 구현 언어 절에는 SQLCipher를
Bun에서 어떻게 쓸지가 없다. 재검토 시 메모리 DB로 직접 확인한 결과:

| 확인 | 결과 |
|---|---|
| Bun 1.3.11의 기본 SQLite 연결 | SQLite 3.51.0, `PRAGMA cipher_version` 결과 `[]` |
| `PRAGMA key`에 테스트 문자열 지정 | 에러 없이 완료. 암호화 성공의 증거가 아님 |
| `Database.setCustomSQLite()` | 함수 존재 확인. SQLCipher 로드는 이번에 미검증 |
| 암호화 파일의 저장·재개방 | 이번에 미검증. 라이브러리 설치 여부도 단정하지 않음 |
| FTS5 trigram | `견적서를 보내주세요`에서 `견적서` 검색 성공, `견적` 미검색 |

SQLite는 알 수 없는 PRAGMA에 오류를 내지 않는다. 따라서 설정 명령의 성공만으로
암호화를 판정하면 평문 저장을 놓칠 수 있다. [SQLite PRAGMA 문서](https://www.sqlite.org/pragma.html).

**제안.**

- 실제 메시지를 저장하기 전에 FTS5와 암호화가 함께 동작하는 파일 DB 스파이크를
  진행한다. macOS에서는 DB 생성 전에 `setCustomSQLite`로 dylib를 지정하는 경로를
  검토할 수 있다. 다른 OS에서는 해당 API가 no-op이므로 이 경로를 그대로 일반화하지
  않는다. 소요 시간과 SQLCipher 호환성은 미확정이다. [Bun SQLite 문서](https://bun.sh/docs/runtime/sqlite#loadextension).
- SQLCipher를 선택했다면 `cipher_version`이 비어 있을 때 진단 실패로 처리한다.
  다만 이 값은 라이브러리 버전이며 **대상 파일의 암호화 증명은 아니다**.
  [SQLCipher API 문서](https://www.zetetic.net/sqlcipher/sqlcipher-api/#cipher_version).
- 실제 저장 경로로 생성한 fixture DB를 닫고 새 연결에서 검사한다. 올바른 키로
  본문·FTS 검색이 복원되고, 키 없음·틀린 키·일반 SQLite로는 본문과 스키마를 읽지
  못해야 한다. WAL과 백업을 사용하는 경우 그 경로도 포함한다. 암호화 확인 실패 시
  실제 메시지 저장을 중단한다. 이 검증을 기존 완료 조건의 구체적인 증거로 삼는다.
- 암호화는 키와 분리된 DB 파일의 유출에 대비한다. 키나 복호화 API에 접근 가능한
  에이전트까지 막는 것은 아니므로 3번의 접근 경계와 구분한다.

### 5. 백필·실시간 이벤트의 중복과 역순 적용 규칙

03-proposal은 `fetchHistorical`·`watch`와 수정·삭제 필드를 정의하지만,
두 경로의 이벤트가 충돌할 때 어느 상태를 채택할지는 정하지 않았다.
실시간 수정 B를 저장한 뒤 지연된 백필 A가 도착하면 단순 upsert는 본문을 과거로
되돌린다. 삭제 뒤 과거 생성 이벤트가 재생되면 tombstone이 사라질 수도 있다.
저장·cursor·coverage의 원자성만으로 적용 순서까지 해결되지는 않는다.

**제안.** 플랫폼·계정·채팅·원본 메시지 ID의 식별 범위를 고정하고, 어댑터가 제공하는
revision 또는 변경 순서를 기준으로 store의 적용 규칙을 정의한다. 수신 시각을 원본
변경 순서로 대체하지 않는다. 순서 정보가 없으면 재조회 또는 미확인 처리 방법을 정한다.
생성보다 삭제가 먼저 와도 식별 키만으로 tombstone을 남기고, 채택한 상태와 FTS를
동일 트랜잭션에서 갱신한다. 추가 이벤트 인프라는 필요하지 않다.

**검증:** 동일 이벤트 반복, 수정 뒤 오래된 백필, 삭제 뒤 생성 재생, 생성보다 먼저
도착한 삭제에서 최신 상태가 유지되고 메시지와 FTS 결과가 일치해야 한다.

### 6. outbox 선점과 재시작의 영속 상태

03-proposal의 Uncertain 자동 재전송 금지 원칙은 맞다. 다만 원격 발송 성공 직후
receipt 저장 전에 종료되면, 로컬에 승인 상태만 남아 미발송 건과 구분되지 않을 수 있다.
동일 승인 건을 두 실행기가 동시에 읽는 경우도 시간창·내용 해시만으로 방지되지 않는다.
1번은 실행 주체를 정하는 일이고, 여기서는 그 주체가 지킬 저장 계약이 필요하다.

**제안.** 원격 호출 전에 승인 유효성·허용 범위·quota를 확인하고
`Approved → Sending`을 원자적으로 선점·커밋한다. 성공한 실행기만 고정된 attempt ID와
불변 payload로 발송하고, 네트워크 대기 동안 DB 트랜잭션을 열어두지 않는다.
receipt가 확인되면 `Verified`, 종료된 실행기의 미완료 `Sending`은 `Uncertain`으로
취급한다. 호출 직전 종료되어 실제 미발송일 수도 있지만 기존 원칙대로 자동 재전송하지
않는다. 살아 있는 실행기의 발송을 시간 초과만으로 회수해 다시 보내서도 안 된다.

같은 승인 건의 중복 실행 차단과, 사용자가 별도로 승인한 동일 본문의 발송을 구분한다.
단일 실행기 모델도 가능하지만 원격 성공과 로컬 기록 사이의 종료 처리는 여전히 필요하다.

**검증:** 동일 승인 건의 동시 실행에서 원격 호출이 한 번인지 확인한다. 선점 직후와
원격 성공 직후 종료를 각각 주입하고, 재시작 후 자동 발송 없이 미확정 상태가 표시되는지
확인한다. 원격 exactly-once 보장을 새로 요구하는 것이 아니다.

## 사소한 것 (선택)

- **unread 비교 기준.** ID가 모든 플랫폼에서 비교 가능한 순서라는 가정은 피한다.
  그렇다고 `ts`로 바꾸면 자동 해결되는 것도 아니다. 동일 시각 메시지와 원본 읽음
  cursor 의미를 고려해 어댑터가 비교 규칙을 정하고, 알 수 없으면 기존 `unknown`을
  유지한다. 현재 구현 오류로 단정하거나 스키마 변경을 필수로 요구하지 않는다.

## 하지 않는 제안

- 언어·패키지 구조·Gateway 인터페이스 교체, MVP 기능 범위 확대. 현행 방향을 유지한다.
- 기존 승인·Uncertain 정책은 유지하며 6번은 그 정책을 실행 가능한 저장 계약으로 구체화한다.
- Beeper 통합 앞당기기, 어댑터 추가, 검색 엔진 선택. roadmap의 게이트 판단이 맞다.

## 이번 재검토에서 보완한 범위

기존 리뷰가 추가한 실행 주체·coverage·승인 접근 경계·암호화 검증 관점은 유용하므로
유지했다. 채팅당 한 행, DB 직접 접근 필수, DB 분리·HMAC만으로 승인 보호가 된다는
전제는 수정했다. 암호화 검증은 버전 확인을 넘어 파일 재개방 기준으로 보완했다.
이전 초안의 이벤트 순서·outbox 재시작 계약은 각각 5·6번으로 추가했다.

이 문서는 제안이며 03-proposal과 04-roadmap의 결정을 변경하지 않는다. 이번 검증은
Bun 메모리 DB 진단과 공식 문서 대조까지다. 암호화 파일 스파이크, 외부 어댑터 소스
재검증, 구현 테스트를 완료했다고 주장하지 않는다.

후속 worktree의 Spike A와 KakaoTalk·Telegram wrapper 코드는 feasibility evidence다.
Spike A는 PARTIAL이고 multiplatform 결과는 synthetic/live-blocked이므로, 이 설계 리뷰를
제품 구현 검증이나 원래 Kakao Spike B 완료로 승격하지 않는다.
