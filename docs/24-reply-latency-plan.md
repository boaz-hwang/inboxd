# 추천 첫 초안 정확도와 1초 생성 — 구체 실행 계획 (보류: 정확도 복구 우선)

> 최신 사용자 지시: 기존 판단·검증 로직을 유지한다. 우선 실제 생성 실패를 분석·수정하고 정확한 추천이 정상 생성되도록 한다. 아래 단일 생성/검증 제거 실험 계획은 보류되었으며 승인되지 않았다. 1초 최적화보다 정확도와 첫 시도 정상 생성이 우선이다.

작성: 2026-09-23. 사용자가 첫 제안에 대해 구체화 후 승인을 선택했다. 아래 최적화는 아직 실행하지 않는다.

## 0. 이미 승인되어 진행 중인 작업

전체 방 생성 유지, 자동 재시도 제거와 실패 기록, 안 읽은 방 우선/그룹 내 최신 수신 순서, 이 Mac에서 작업자 병렬화 실측은 별도 승인 범위다. 이 문서의 승인을 기다리지 않고 진행한다.

## 1. 목표와 변경 경계

목표: **대화 입력을 받은 모델이 첫 시도에 문맥에 맞는 추천 전체를 1초 이내 생성**하도록 만든다. 최종 지향점은 판단용·검증용 별도 LLM 호출 없이 생성 1회다. 사용자에게 보이는 실제 대기 시간은 큐 대기를 포함해서 별도로 측정한다. 캐시 조회나 첫 토큰 시간을 생성 시간으로 보고하지 않는다.

- 예열된 모델의 짧은 대화(본문 입력 2,000 tokens 이하)에서 첫 생성 완료 p95 < 1,000ms를 1차 성능 통과 기준으로 삼는다. 이 수치는 달성 사실이 아니라 검증할 목표다.
- 긴 대화(최대 현재 제품의 최근 40개 메시지), 첫 모델 로드, 다수 방 동시 도착은 별도 지연 분포로 공개한다. 이 경우까지 1초가 된다고 미리 약속하지 않는다.
- 품질이 확보되지 않으면 검증을 끄거나 모델을 교체하여 시간만 맞추지 않는다. 실패 시 기본 문구·자동 재생성 없이 실패 표시와 원인 기록을 남긴다.
- 초안은 자동 전송하지 않는다. 빈 출력, 통신/형식 오류, 출력 중단, 문맥 버전 불일치 같은 프로그램 검사는 단일 생성에서도 유지한다.

기준선: 과거 9B 초안 생성 p50/p95 1.11/1.37초(20건), 기존 통합 경로 중앙값 8.70초(6건). 과거 4B는 0.70/0.91초였으나 중대 오류가 7/20으로 9B의 1/20보다 많았다. 과거 프롬프트와 표본의 결과이므로 이번 기준선은 다시 측정한다. 출처: `docs/23-local-model-evaluation.md`.

## 2. 먼저 해결할 실패 유형과 구체 입력 계약

| 실패 | 생성 전에 해결할 내용 | 해결했다고 볼 조건 |
| --- | --- | --- |
| 내 말을 상대의 말로 착각 | 계정의 own_id로 발화자 결정, 실제 user/assistant 역할 전달, 마지막 내 발화와 상대 발화를 각각 식별 | 본인이 보낸 파일을 본인이 받았다고 답하지 않음 |
| 단체방 대상 착각 | author_id, reply_to, 실제 제공되는 mention/수신 대상 유지. 대상 정보가 없으면 unknown으로 전달 | 다른 사람에게 온 질문을 본인의 약속으로 답하지 않음 |
| 일정·가격·진행 의사 창작 | 원문 근거와 출처 ID 제공, 사실과 사용자 결정 구분. 없는 일정/의사/수행 결과를 unknown으로 둠 | 과거 단가를 안다는 이유로 새 계약에 동의하지 않음 |
| 부정·정정·조건 누락 | 정정 순서와 reply 연결 보존, 조건문/금지 원문을 문맥에서 잃지 않게 함 | 금요일→월요일 정정, 전달 금지, 조건부 수락을 유지 |
| 과거 사실 부족 | 이미 저장된 같은 방의 reply 연결 및 관련 원문을 생성 전에 확보. 가져오지 못한 사실은 미확정 | 자료가 없는데 확인/조회 완료라고 쓰지 않음 |
| 읽은 방의 어색한 후속 발화 | unread 여부와 대화의 마지막 발화자를 분리. 이미 끝난 대화도 자연스러운 후속 초안으로 평가 | 본인의 말을 반복하거나 고정 인사로 채우지 않음 |
| 내부 이벤트·삭제/수정 오염 | 정규화된 실제 메시지만 사용하고 snapshot version 고정 | logId 메타데이터를 대화로 답하지 않음 |
| 검증기의 오판·형식 오류 | 생성 오류와 검사기 오판을 분리해 기록하고 typed 결과 파싱 테스트 | 좋은 초안을 reasonCode 누락만으로 실패 처리하지 않음 |

구조화 입력은 원문을 버리고 추정한 요약으로 대체하지 않는다. 의미상 ‘확정된 사실’을 완벽하게 추출하는 코드를 만들 수 있다고 가정하지 않는다. 코드로 확실히 알 수 있는 발화자·시간·연결은 코드가 결정하고, 해석이 필요한 내용은 출처가 붙은 원문으로 모델에 전달한다.

## 3. 평가 데이터와 통과 기준

### 데이터

- 기존 20건은 과거 프롬프트 개선에 노출됐으므로 개발 사례로만 사용한다. ‘추천 없음’을 정답으로 하던 기존 기준은 현재 요구에 맞게 다시 작성한다.
- 위 8개 실패 유형별 새 사례 15건씩, 총 120건을 작성한다. 각 유형 5건(총 40건)은 개발용, 10건(총 80건)은 미사용 평가용으로 미리 고정한다.
- 사례마다 답변에서 보존할 사실, 금지할 주장, 답변 대상, 허용되는 확인 질문을 먼저 적는다. ‘정답 문장 하나’와의 일치로 채점하지 않는다.
- 실제 실패는 익명화한 재현 사례로 개발 세트에 넣고, 실사용 대화 원문을 공개 벤치마크 파일에 저장하지 않는다. 새 사용자 데이터 학습은 이 승인 범위에 넣지 않는다.

### 품질 판정

- **중대 오류 0/80**: 역할/대상 반전, 사실·행동·일정·승낙 창작, 명시한 금지/정정 위반. 하나라도 있으면 검증 제거 후보를 채택하지 않는다.
- **첫 시도 유효 초안 76/80 이상**: 사실 준수뿐 아니라 자연스러움, 질문에 대한 관련성, 필요한 항목 누락 없음. 답을 알면서 전부 질문으로 돌리는 것은 통과시키지 않는다.
- 현재 경로와 같은 입력으로 비교해 중대 오류·유효 초안 비율 모두 악화되지 않아야 한다. 생성 실패도 분모에 포함한다.
- 생성 모델 자신의 supported/confidence 값은 품질 증거로 사용하지 않는다. 사전 기준으로 별도 검토자가 판정하고 애매한 사례는 메인 에이전트가 원문과 대조한다. 필요하면 사용자에게 구체 사례를 보여 판단받는다.
- 80건 통과는 미래 오류 0을 보장하지 않는다. 평가 세트를 본 뒤 수정했다면 그 세트는 개발용으로 전환하고 새로운 미사용 사례로 다시 확인한다.

### 시간 판정

- 동일 기기/모델/입력/출력 상한을 고정하고 첫 실행과 예열 후 실행을 분리한다. 입력·출력 tokens와 지연을 함께 저장한다.
- queue 대기 / context 준비 / 모델 로드 / 판단 / 생성 / 검증 / UI 전달을 따로 기록한다. step 합계만으로 실제 사용자 대기 시간을 대신하지 않는다.
- 예열 5건 이후 첫 시도 80건을 측정하고 짧은/긴 대화의 p50/p95, 실패율, 메모리와 동시 작업 수를 보고한다. 출력 길이를 강제로 잘라 1초를 맞춘 결과는 실패다.

## 4. 구현·실험 순서와 산출물

### A. 기준선과 실패 지도

현 파이프라인의 첫 시도만 계측한다. 입력 snapshot/문맥 버전, 단계별 시간, 출력, 실패 phase/reasonCode를 연결한다. **산출물:** 현재 p50/p95/첫 시도 성공률, 유형별 실패 목록, 재현 fixture. 이 단계에서는 모델 동작을 바꾸지 않는다.

### B. 입력만 개선

위 입력 계약을 compiler/storage 경계에 적용한다. 모델·생성 횟수·검증 경로는 고정한다. 변경 하나마다 개발 사례의 역할·근거·부정/정정 오류 감소를 확인한다. **산출물:** 최소 코드 변경, 입력 전후 비교, 실패가 실제 줄었는지 표. 효과 없는 프롬프트 문장은 쌓지 않는다.

### C. 단일 생성 후보 비교

동일 입력에 대해 (1) 기존 판단→생성→검증과 (2) 추가 판단·검증 LLM 없는 생성 1회를 비교한다. 후보 (2)의 검증은 사용자 응답 경로 밖의 오프라인 평가로 수행한다. 전체 방에 초안을 제공해야 하므로 단순 응답 필요 여부 판정용 호출을 반드시 유지할 이유가 있는지도 재검토한다. 근거가 부족하면 문맥에 맞는 미확정 표현을 사용하며 고정 기본 문구로 대체하지 않는다.

**산출물:** 미사용 80건 품질표, 실패별 원문 근거, 전체 지연 비교, 검증 제거 가능/불가 결론. 품질 기준을 만족하지 않으면 제품 경로의 검증은 유지하고 남은 원인을 보고한다.

### D. 9B 속도 실험

품질을 보존한 후보에서 모델 상주·동일 프롬프트 접두부 캐시·중복 입력 제거를 한 변수씩 실험한다. 캐시가 현재 MLX 코드 경로에서 실제 지원/효과가 있는지 검증하고, 문맥·모델·개인화 변경 시 무효화를 테스트한다. 최대 40개를 무조건 짧게 자르는 방식은 쓰지 않는다.

**산출물:** 항목별 시간 절감/메모리/오류 영향. 여전히 1초를 넘으면 현재 하드웨어·출력 길이에서 가능한 시간을 제시한다.

### E. 필요할 경우에만 추가 제안

9B로 목표를 달성하지 못하면 작은 모델/개인화 학습을 별도 제안한다. 입력 개선과 모델 변경 효과를 섞지 않는다. 어떤 교정 데이터가 얼마나 필요한지, 기존 4B 오류를 줄일 가능성, 데이터 사용 범위와 결과 검증 방법을 제시하고 승인을 받은 후 진행한다.

## 5. 승인 범위

이번 승인 요청은 **A–D 계측·입력 개선·격리 실험과 평가**까지다. 현재 생성기의 검증 제거를 미리 승인받는 요청이 아니다. 통과 기준 충족 여부와 실제 출력 사례를 메인 에이전트가 보고한 뒤 제품 경로 전환 여부를 확인받는다. 모델 교체/사용자 데이터 학습(E)은 별도 승인이다.
