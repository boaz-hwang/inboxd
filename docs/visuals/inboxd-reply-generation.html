추천 하나가 만들어지는 전체 흐름

로컬 모델이 판단·작성·검사를 맡고, Rust 데몬이 실행 범위와 저장 상태를 통제합니다. 사용자에게 도달한 초안도 사용자가 수락하고 전송해야 메시지가 됩니다.

대화 스냅샷최근 메시지와 내 계정 식별
실행 큐안 읽은 방부터 처리
문맥 판단바로 답장 / 검색 / 재판단
작성 + 검사초안 1회, 근거 검사 1회
사용자 선택추천 확인 → 수락 → 전송

기본 모델

Qwen3.5-9B-4bit

MLX 로컬 모델의 코드상 기본값입니다. 환경 변수로 교체할 수 있습니다.

외부 정보 범위

현재 방의 저장 기록

메일·캘린더·파일·다른 방·링크 목적지는 현재 검색 소스가 아닙니다.

생성 원칙

모든 유효 문맥에 다음 초안

읽은 방도 대상입니다. 문맥이나 내 계정 정보가 없으면 준비 단계에서 중단합니다.

이 문서는 2026-09-23 작업 트리의 구현을 설명합니다. 미커밋·신규 파일을 포함하며, 실행 중인 데몬 바이너리와 설치된 Python 파일이 같은 버전인지는 검증하지 않았습니다. 실사용 대화나 삼성물산 방의 원문은 포함하지 않았습니다.

대화는 어떤 데이터로 들어오는가

저장소가 발화자를 먼저 구분합니다. 모델이 이름이나 말투로 “나”를 추측하는 구조가 아닙니다.

messages 조회삭제되지 않은 최근 40개
시간순 재정렬오래된 말 → 최신 말
계정 ID 비교self / other / unknown
버전 고정문맥 + 런타임 + 대상 ID
입력 필드실제 의미읽을 때 주의할 점
message_id / author_id메시지 및 발화자 ID계정의 self_id와 일치하면 self, 다른 알려진 ID면 other
body / ts / reply_to본문·시각·부모 메시지 ID최근 40개에는 삭제 메시지를 제외. 수정된 본문은 새 문맥에 반영
incoming_message_ids현재 대응 범위의 미열람 메시지 ID최근 모든 상대 발언과 같지 않음. 읽은 방에서는 비어도 생성 가능
context_version문맥 JSON + runtime_version + 대상 ID의 SHA-256prompt_version과 함께 같은 추천인지 식별
source_registry / evidence허용 출처 목록 / 추가 검색 원문모델이 임의로 출처를 등록할 수 없음

판단용 build_state

본문 예산 32,000자. incoming 메시지를 최신순으로 먼저 확보한 뒤 나머지 최근 문맥을 채웁니다. 누락·본문 절단·불명 필드·같은 출처의 상충 내용을 구조화합니다.

state_id는 의미 상태로 만듭니다. 실행 횟수는 해시에서 제외하므로 같은 상태를 반복 재판단하는지 알 수 있습니다.

작성용 compile_prompt

대화 JSON이 32,000자를 넘으면 오래된 메시지부터 제거하고 누락 ID를 남깁니다. 남은 첫 메시지 본문이 16,000자를 넘으면 오류로 처리합니다.

Telegram의 정확한 [ChatDeleteMember] 표시는 제외합니다. 판단 입력과 작성 입력의 절단 방식은 같지 않습니다.

입력 경계의 한계: build_state의 절단 표시는 전달받은 문맥 안에서 발생한 누락입니다. 저장소에서 처음부터 최근 40개 밖으로 제외된 전체 과거 기록까지 포괄하는 완전성 증거는 아닙니다.

04 / LOGIC

모델 판단과 실행 정책은 분리돼 있다

모델은 일곱 필드의 선택형 JSON을 냅니다. Python이 형식을 검증하고, 결정적인 규칙으로 다음 행동을 선택합니다.

로컬 LLM선택형 JSON 한 개
계약 검증선택지·타입·출처 ID 확인
정책 실행권한·불확실성·예산 적용
Rust 실행검색 범위와 횟수 재검사
필드선택지 / 의미
responserespond / no_reply / uncertain
sufficiencysufficient / insufficient / unknown
gapsprevious_agreement · availability · project_state · user_decision · other · unknown · not_applicable
sources등록된 source ID만 선택. 현재는 current_chat_history
risksunsupported_commitment · sensitive_context · conflicting_evidence · other · unknown · not_applicable
escalationdirect / retrieve / reason / clarify / defer
uncertaintrue / false
0과 1은 신뢰도 확률이 아닙니다. 현재 baseline은 선택한 범주를 1, 나머지를 0으로 변환한 categorical_indicator입니다. 범주별 학습 헤드를 가진 별도 CIM이나 보정된 확률 모델로 설명하면 부정확합니다.
정확한 파싱 규칙과 점수형 인터페이스

판단 출력은 JSON 객체여야 하며 코드 펜스·추가 필드·중복 배열 항목·등록되지 않은 출처를 거부합니다. 제한된 별칭만 허용합니다: response=clarify는 escalation=clarify일 때 respond로, sufficiency=direct는 응답 의사가 명확하고 불확실하지 않은 direct 판단에서 sufficient로 보정합니다.

일반 점수형 인터페이스는 임계값 0.55, response 상위 두 점수 차이 0.15를 사용합니다. 현재 범주형 baseline의 낮은 신뢰 판단은 uncertain 선택/플래그를 사용하므로 이 숫자를 “55% 이상이면 답장”으로 해석하면 안 됩니다.

05 / LOGIC

분기는 위에서부터 먼저 맞는 규칙을 따른다

“검색할 수 있다”는 사실과 “사용자가 승인했다”는 사실은 별개입니다. 새 승낙·일정 확정·선호 결정이 필요하면 검색보다 확인 질문이 앞섭니다.

순서조건정책의 다음 행동
1명확한 no_reply이고 중대한 불확실성이 없음no_reply → 상위 데몬은 후속 reply 생성으로 변환
2user_decision 정보가 부족함clarify — 검색으로 사용자 결정을 대신하지 않음
3uncertain, 문맥 충분성 unknown, reason 요청 또는 중요 불확실성같은 state에서 reason 1회. 이후에도 남으면 gap/충돌이 있으면 clarify, 없으면 defer
4sufficient인데 retrieve를 요청한 모순reason 1회 → 미해결이면 clarify
5insufficient 또는 retrieve 요청허용된 새 검색 + 남은 예산이 있으면 retrieve. 없으면 gap 유무에 따라 clarify/defer
6sufficient + directunsupported_commitment 위험이 있으면 clarify, 없으면 reply
7escalation=clarifyclarify
8나머지defer → 상위 데몬은 clarify 생성으로 변환

위 전환은 결과가 아직 없는 정상 종료 경로에 적용됩니다. 판단 형식 오류·검색 범위 위반 등으로 이미 실패 결과가 생긴 경우에는 초안 생성으로 우회하지 않습니다. 보완 초안에도 같은 근거 검사를 적용합니다.

검색 결과를 받아 다시 판단할 수 있지만 무제한 에이전트 루프는 아닙니다. Rust가 검색할 계정과 방을 고정하고 중복 호출을 막습니다.

07 / LOGIC

초안은 “내가 보낼 말”로 한 번 작성한다

문맥을 JSON으로만 전달하지 않고 실제 채팅 역할에도 반영합니다. 내 이전 발언은 assistant, 상대 및 unknown 발언은 user 역할로 넣습니다.

경우작성 방향
마지막 발언이 상대reply_other: 상대에게 보낼 답장
마지막 발언이 나continue_self: 내 발언을 받은 것처럼 답하지 않고 후속 확인 질문 작성
clarify 전략내 일정·승인·선호가 없음을 내 관점에서 표현. 상대의 질문을 그대로 되묻지 않음
URL이 있고 검색 근거가 없음링크를 열어 확인한 것으로 쓰지 말라는 추가 지시
개인화 어댑터활성 레지스트리, 기본 모델 ID, 학습 manifest, 가중치 digest가 맞을 때 작성 단계에만 적용

작성 상한은 192토큰, temperature는 0입니다. 판단에는 최대 900토큰, 검사에는 최대 256토큰을 사용합니다. thinking은 꺼져 있으며, 남은 think 태그·빈 출력·<ABSTAIN>은 정상 추천으로 표시하지 않습니다. 상한 숫자는 모델 호출의 제한이며 문장 품질이나 지연 보장값은 아닙니다.

개인화가 바꿀 수 있는 범위

개인화는 문구 작성에 적용됩니다. 판단과 근거 검사는 기본 모델로 실행하며, source 권한이나 전송 권한은 바꾸지 않습니다. 활성 어댑터가 없는 경우 기본 모델을 사용합니다. 이 문서는 현재 계정에서 어댑터가 실제 활성인지 확인한 결과가 아닙니다.

승인 조건

supported === true이며 reasonCode가 grounded 또는 없음/null인 경우 통과합니다. 코드를 생략한 명시적 승인을 형식 누락만으로 버리지 않습니다.

보류·오류 조건

false, 잘못된 JSON, true와 거부 코드의 모순 등은 보류합니다. 내부 create_reply의 abstained는 handle에서 failed로 바뀌며 추천 본문은 null이 됩니다.

검사에 실패해도 다른 초안을 자동으로 다시 만들지 않습니다. 오류 원인과 생성·검사 입력을 trajectory에 남겨 분석합니다. 이 경로에는 문맥과 무관한 고정 답변 fallback이 없습니다.

현재 구현의 경계와 지연을 읽는 법

초안 작성 한 번의 시간과 사용자가 추천을 기다리는 전체 시간은 다릅니다. 검색과 재판단이 필요한 방은 모델 호출 수가 늘어납니다.

상황모델 호출 구조
일반 직접 답장판단 1 + 작성 1 + 검사 1 = 3회
같은 상태 재판단 1회판단 2 + 작성 1 + 검사 1 = 4회
검색 또는 추가 상태 변화판단 루프 최대 6회 + 작성 1 + 검사 1. 실패 시 더 일찍 종료 가능
작업자 2개여러 방의 대기 해소 목적. 같은 GPU 경쟁으로 개별 지연이 늘 수 있음

코드에서 확인한 현재 동작

판단·검색·생성·검사 경로, 같은 문맥의 실패 유지, 읽은 방도 추천, 로컬 모델 및 제한된 검색 범위가 구현돼 있습니다.

아직 현재 동작으로 쓰면 안 되는 것

생성 1회만으로 끝나는 구조, 검사 제거, 모든 추천 1초 완료는 현재 구현이 아닙니다. 관련 지연 최적화 문서는 보류 상태입니다.

코드 검토로 드러나는 해석상의 주의점

  • 판단기가 no_reply를 낼 수 있지만 데몬은 후속 초안으로 전환합니다. UI의 “추천 없음”과 같은 뜻이 아닙니다.
  • 정책에는 sensitive_context 등 위험 라벨이 있지만, 모든 라벨이 독립적인 차단 분기로 구현된 것은 아닙니다. 명시적 주요 분기는 conflicting_evidence와 unsupported_commitment입니다.
  • 프롬프트에서 URL 확인을 금지해도 실제 검증은 모델 판단입니다. URL을 열어 사실을 검증하는 기능은 없습니다.
  • 판단과 작성의 입력 절단 방식이 달라 완전히 같은 본문을 항상 보는 것은 아닙니다.
  • 기존 logId 노출 문제의 해결 여부는 이 문서의 검증 범위에 포함하지 않았습니다. 추천 입력 품질은 상류 메시지 정규화에도 의존합니다.
