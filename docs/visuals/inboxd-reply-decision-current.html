추천 메시지는 어떤 대화를 보고
어떻게 답장 방향을 정할까?

현재 코드의 대화 준비와 판단·검색 경로를 설명합니다. 이 페이지의 숫자는 작업 트리의 구현값이며 품질 최적값이라는 뜻은 아닙니다.

확인일: 2026-09-23 · 설명 범위: 최근 대화 선택 → 판단 → 검색·재판단 → 초안 방향

1. 왜 최근 40개인가?

40개한 방에서 가져오는 최근 메시지 수의 상한. 나와 상대의 메시지를 합산합니다.
32,000자판단용 본문 예산. 긴 대화에서는 40개를 모두 담지 못할 수 있습니다.
0건40이라는 값의 선택 근거로 코드에 기록된 실험·측정 결과.
정확한 해석
40은 저장소 조회문의 고정 상한입니다. “40개가 가장 정확하고 빠르다”는 검증 결과는 코드에서 확인되지 않습니다. 오래된 합의가 이 범위 밖에 있으면 뒤의 검색 경로에 의존합니다.

판단용 상태는 새로 들어온 메시지의 본문을 우선 담고, 남은 공간을 최근 대화로 채웁니다. 초안 작성에는 별도의 길이 제한이 적용되어 판단과 작성이 보는 본문 범위가 달라질 수 있습니다.

마지막 실제 발신자가 나이면 추천을 준비하지 않습니다. 상대가 마지막으로 말했으면 이미 읽은 방도 추천 대상이 될 수 있습니다.

코드: 대화 조회·대상 판별판단 입력 구성작성 입력 제한

2. 답장 방향은 어떻게 결정하나?

① 상태 구성최근 대화, 발신자, 새 메시지 ID, 기존 근거와 검색 출처를 묶습니다.
② 모델 분류답장 필요성, 정보 충분성, 부족한 정보, 위험, 다음 행동을 JSON으로 고릅니다.
③ 정책 검사코드가 출력 형식과 허용 범위, 사용자 결정·불확실성 규칙을 확인합니다.
④ 검색·재판단필요하면 같은 방의 이전 기록을 찾고 근거를 더해 다시 분류합니다.
⑤ 방향 확정reply 또는 clarify를 초안 작성기로 전달합니다.

모델은 답장 문장보다 먼저 이 항목을 고릅니다

항목선택 예시의미
답장 필요성respond · no_reply · uncertain답할 상황인지
정보 충분성sufficient · insufficient · unknown지금 가진 근거로 답할 수 있는지
부족한 정보이전 합의 · 일정 · 프로젝트 상태 · 내 결정무엇을 확인해야 하는지
위험근거 없는 확정 · 근거 충돌그대로 답하면 사실이나 의사를 잘못 단정할지
다음 행동직접 답장 · 검색 · 재판단 · 확인 질문 · 보류코드에 제안하는 다음 단계

코드: 분류 항목·프롬프트·출력 검증로컬 모델 호출

3. 모델의 제안을 코드가 어떻게 처리하나?

내 새 결정이 필요함

계약 승낙이나 내 일정 가능 여부를 과거 기록으로 대신 확정하지 않습니다. clarify를 선택합니다.

불확실하거나 모순됨

같은 상태를 한 번 더 판단합니다. 해결되지 않으면 확인 질문이나 보류 방향으로 갑니다.

이전 정보가 필요함

현재 방의 저장 메시지만 검색합니다. 최대 2라운드, 총 3회 질의 후 검색 결과를 근거에 추가해 다시 판단합니다.

지금 정보로 충분함

근거 없는 확정 위험이 없으면 reply, 위험이 있으면 clarify를 선택합니다.

no_reply의 현재 동작
마지막 발신자가 상대여서 여기까지 온 경우, 모델의 최종 no_reply는 초안 작성 전에 reply로, defer는 clarify로 전환됩니다. 마지막 발신자가 나인 경우는 대화 준비에서 이미 중단됩니다.

코드: 정책 분기검색·반복·최종 전환

4. 세 가지 상황으로 보기

“자료 감사합니다.”

현재 대화로 답할 수 있다고 판단하면 reply로 갑니다.

“지난번 조건으로 할까요?”

이전 합의가 필요하면 같은 방의 과거 기록을 검색하고 다시 판단합니다.

“내일 3시 가능하세요?”

내 일정·결정의 근거가 없으면 가능하다고 확정하지 않는 clarify로 갑니다.

예시는 처리 경로를 설명하기 위한 가상 대화입니다. 실제 모델 출력이나 생성 문구를 보장하지 않습니다. 초안은 별도 근거 검사를 통과해야 추천으로 표시됩니다.
