# 초기 로딩 및 API 호출 최적화 결과

2026-09-19. 구현·로컬 설치 완료. 우선순위는 **캐시 없이 API 호출 자체 절감 → 캐시 → 병렬 처리**다.

## 1. 캐시가 없어도 줄어드는 요청

| 작업 | 변경 전 | 변경 후 | 동일 기능 검증 |
| --- | ---: | ---: | --- |
| Slack 최초 26개 방 목록 | 42회 | 29회 | users.list 1 + 누락 사용자 info 1 + 목록 1 + history 26 |
| Kakao 최초 46개 방 목록 | 54회 | 50회 | 세션 3 + 목록 1 + CHATINFO 46; 추가 멤버 스냅샷 4회 제거 |
| Kakao 8개 방 이력 읽기 | MCHATLOGS 8회 | MCHATLOGS 1회 | 같은 8개 방·같은 시작점·100개 제한으로 실제 응답 페이지 전체 동일 |
| Kakao 작성자 이름 | 이미 이름이 있어도 MEMBER | 응답에 이름이 있으면 0회 | 단위 테스트로 이름 보존·추가 조회 없음 검증 |
| Slack/Telegram 검색 페이지 | 최대 30개 요청 | 최대 100개 요청 | 로컬 전송 페이지로 분할, 커서와 모든 결과 보존 테스트 |
| 전송 후 화면 갱신 | 성공 후 이력 다시 읽기 | 성공 메시지 응답 활용 | 실제 전송 재실행 없이 기존 단위 테스트로 검증 |

Slack 최초 users.list 15명에는 DM 상대 1명이 없어 단건 fallback을 유지한다.
client.counts는 첫 조회에서 제외하여 초기 요청을 늘리지 않는다.

Kakao 제목 조회는 같은 CHATINFO 한 번으로 제목과 멤버 정보를 함께 받아 SDK가
작성자 이름에도 쓰도록 했다. 46개 방의 제목을 기존 결과와 비교하여 차이 0개,
상세 조회 실패 0개를 확인했다. MemoChat의 표시 이름도 기존 멤버 스냅샷과 같았다.
일괄 이력 읽기는 SDK getMessagePage의 응답 검증/포맷/빈 결과 보충 절차를 그대로
사용하고 각 방의 응답을 분리한다. 다른 방의 데이터가 섞이면 실패한다.

첫 목록에서 다른 방들의 CHATINFO 46회를 전부 제거하는 API는 확인하지 못했다.
Slack conversations.list에 no_latest=false를 주어도 latest 메시지 객체는 반환되지
않았고, client.boot도 이번 조회에서 쓸 수 있는 일괄 목록을 주지 않았다.
기능을 생략해서 요청 수를 줄이거나, 전체 최신 데이터 조회가 0회라고 주장하지 않는다.

## 2. 부가 조치: 재사용과 병렬 처리

- 계정별 worker/session을 유지한다. 매 RPC마다 재로그인하지 않고 이름 정보를 버리지 않는다.
- Kakao는 조회한 페이지를 30초 동안 재사용하고 검색어에 맞는 결과의 누락 이름만 조회한다.
- 이미 읽은 Kakao 이력의 마지막 cursor 이후를 수집한다. 원격 수정/삭제 전체를 추적하는
  영속 인덱스나 실시간 동기화는 이번 변경에 포함되지 않는다.
- Slack은 반복 갱신 시 client.counts의 최신/변경/이력 무효화 watermark를 비교한다.
  같은 시각의 수정·삭제도 무효화 watermark가 바뀌면 재조회한다. 응답에 없는 방은 조회한다.
- 목록은 30초 이내 스냅샷이면 즉시 표시하고, 오래되면 계정별로 갱신한다.
- TUI 검색 요청과 서버 read dispatch 모두 병렬화했다. 같은 계정 작업은 직렬화한다.
- 진행 중 목록은 계정별 완료 시 반영한다. 읽기용 스냅샷은 원격 작업 잠금과 분리했고,
  페이지 커서는 불변 스냅샷에 연결해 도중 정렬 변화로 인한 누락을 막는다.
- 응답의 바이트 상한을 지키면서 큰 검색 결과 묶음을 보관하고 로컬 페이지로 나눈다.
- 중단/오류가 난 worker는 폐기한다. 프로토콜 응답이 다음 요청에 섞이지 않게 하며
  전송을 자동으로 재시도하지 않는다. 요청 ID 중복 방지와 소유자 전송 권한을 유지한다.

Kakao 같은 세션의 즉시 재조회 54→0회는 캐시 효과다. 위의 첫 조회 54→50회와 구분한다.
Slack 최초 목록은 실제 측정 3.51초였다. 네트워크 지연에 따라 시간은 달라진다.

## 3. 설치된 TUI 측정

| 측정 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 첫 채팅방 화면 표시 | 4,925ms | 362–2,034ms (최종 재설치 직후 2,034ms) |
| 기존 데몬 목록을 TUI 컨트롤러에 반영 | 강제 전체 갱신 약 5,172ms | 5ms |

첫 화면 비교는 실제 설치 명령을 120×40 PTY에서 실행해 플랫폼 표시를 감지했다.
변경 후 측정 직전에 데몬을 재시작했다. 다만 기존 TUI 두 개의 자동 재연결이
확인되어, 새로 띄운 측정 TUI만의 엄밀한 단독 콜드 스타트라고 볼 수 없다.
최종 재설치 직후에는 헤더 2,003ms, 첫 방 2,034ms였다.
API 호출 수는 별도로 새 어댑터에서 검증한 수치이며 이 화면 측정의 캐시 효과와 구분한다.
메신저 세션 파일·TDLib 로컬 DB·OS 파일 캐시를 삭제한 신규 가입 실험도 아니다.

데몬 재시작 후 별도 컨트롤러 측정에서는 9개 방 1,217ms → 55개 방 1,724ms → 전체 81개 방
5,096ms 순서로 반영됐다. 따라서 **첫 사용 가능 시점 단축과 전체 계정 최신화 완료는 다르다.**
위 수치는 소수 실행의 관측치이며 평균/p95 보장치가 아니다.

## 4. 검증과 남은 범위

- 최종 전체 Bun 테스트 449 통과, opt-in 통합 테스트 13 제외.
- Rust daemon/protocol 테스트, Clippy -D warnings, 타입 검사, 계층 경계 검사 통과.
- background 부분 목록, 느린 다른 계정과 독립된 읽기, 중복 갱신 합치기, 불변 페이지,
  검색 병렬 시작, 종료 후 polling 정지, 배치 응답 분리, 페이지 유실 방지 테스트 추가.
- 최종 설치본의 Telegram·Slack·KakaoTalk 읽기 및 작성자 이름 확인 완료. 이번 작업에서 메시지를 발송하지 않았다.
- 키체인 helper의 기존 지정 요구사항 해시 유지. 재시작 때 새 암호 입력 없이 진행했다.
- 수동 `b` 새로고침은 선택한 방의 Kakao 이력 캐시도 무효화하여 수정된 내용을 재조회한다.
- 캐시는 메모리 범위다. 데몬 재시작 후 복원하는 SQLCipher 스냅샷, 영속 검색 인덱스,
  RTM/LOCO 실시간 구독은 아직 구현하지 않았다.
- 다중방 MCHATLOGS는 현재 계정에서 8개 방까지 동일 결과를 확인했다. 서로 다른 방의
  분량이 매우 크거나 서버가 일부 결과만 반환하는 경우에도 기존 SDK의 eof/cursor 및
  빈 결과 fallback을 사용하며, 수집이 끝나기 전에는 완료로 표시하지 않는다.
