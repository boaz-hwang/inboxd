# 시작 지연 분석

2026-09-19, 현재 설치된 제품과 연결된 개인 계정에서 측정했다.
조회만 실행했으며 메시지 전송은 하지 않았다. 시간·요청 수·방 수만 기록했다.
아래 개선안은 아직 제품 코드에 적용하지 않았다.

## 결론과 측정

첫 화면이 모든 메신저의 원격 채팅 목록 조회 완료에 의존한다.
Slack의 방별 최신 메시지·이름 조회가 전체 화면 표시를 지연시킨다.
데몬에 목록이 이미 있어도 TUI 시작 시 강제로 다시 조회한다.

| 대상 | 측정 결과 | 범위 |
| --- | ---: | --- |
| 실행 중인 데몬 준비 확인 | 1–3ms | 소켓 연결 및 상태 확인 |
| 데몬 종료 + 새 시작 + 준비 확인 | 166ms | 키체인·DB 열기 포함; 컴퓨터 재부팅 측정 아님 |
| 프로토콜 handshake | 1ms | 컨트롤러 측정 |
| 원격 전체 목록 조회 | 5,169 / 5,976ms | 각각 기존 데몬 / 새로 시작한 데몬 |
| 첫 전체 목록 상태 반영 | 5,172 / 5,979ms | 81개 방, 모든 페이지 수신 후 |
| 진단 조회 합계 | 약 1ms | system.status, sync.status, auth.status |
| 캐시 사용 비교 실험 | 3ms | 81개 방 상태 반영; 화면 렌더링 제외 |
| 설치된 TUI 첫 헤더 | 583ms | 120×40 PTY, 실행부터 계산 |
| 설치된 TUI 첫 채팅방 표시 | 4,925ms | 같은 PTY 실행, 첫 [KK] 감지 |

개별 설치 워커를 병렬 실행한 조회:

| 메신저 | 완료 | 방 수 |
| --- | ---: | ---: |
| Telegram | 83ms | 9 |
| KakaoTalk | 1,037ms | 46 |
| Slack | 5,641ms | 26 |

별도 Slack 소스 어댑터 호출은 5,988ms, 총 42회 HTTP 요청이었다.

| API | 횟수 | 요청 시간 합계 |
| --- | ---: | ---: |
| conversations.list | 1 | 566ms |
| conversations.history | 26 | 10,211ms |
| users.info | 15 | 5,293ms |

최대 3개 동시 실행이므로 요청 시간 합계는 실제 경과 시간보다 크다.
소수 실행의 관측치이며 평균·p95 또는 모든 계정에 대한 보장치가 아니다.
캐시 실험은 테스트 래퍼에서 account.list의 refresh만 false로 바꿨다.
인증·갱신을 포함한 완성된 개선 구현의 성능으로 해석하면 안 된다.

## 코드상 원인

1. `packages/tui/src/index.ts`의 `refresh()`는 최초 계정 모드 판별에
   `account.list { refresh: true }`를 사용한다. 재실행도 캐시를 우회한다.
2. `crates/inboxd-daemon/src/accounts.rs`의 `list()`는 계정별 조회를
   병렬 실행하지만 JoinSet 전체 완료 후 응답한다. 빠른 계정도 Slack을 기다린다.
3. `platforms/slack/src/account.ts`는 방별 이름과 최근 메시지를 추가 조회한다.
   이번에는 26개 방 모두 history 조회가 발생했다. 방 수에 따라 요청이 증가한다.
4. 워커는 요청마다 새 프로세스라 어댑터의 이름 Map도 재사용되지 않는다.
   단, 이번 측정에서 프로세스 시작 자체가 주원인은 아니다.
5. TUI는 모든 목록 페이지를 받은 후 상태를 반영한다. 이번 후속 페이지는
   각각 1ms 미만이어서 페이지 수보다 서버의 전체 완료 대기가 문제다.
6. 목록 캐시는 데몬 메모리에만 있어 데몬 재시작 시 사라진다.

또한 `workspace.ts`는 조회 중 빈 목록도 “연결된 대화 없음”으로 표시한다.
로딩과 실제 빈 결과를 구분하지 않아 연결 오류처럼 보일 수 있다.

## 권장 변경 순서

### 1. 목록 읽기와 갱신 작업 분리

TUI는 현재 스냅샷을 즉시 읽고, 데몬이 별도로 갱신한다. 메신저별 완료를
이벤트 또는 짧은 상태 조회로 반영한다. 캐시 없는 최초 실행도 Telegram과
KakaoTalk부터 사용할 수 있게 한다. Slack의 지연·실패가 다른 계정을 막지 않는다.

```text
현재: 실행 → 전체 원격 조회 → 가장 느린 계정 완료 → 전체 표시
변경: 실행 → 기존 목록 표시
                └→ 계정별 갱신 → 완료된 계정부터 화면 갱신
```

현재 Slot mutex는 원격 워커 실행 내내 잠겨 있다. 작업을 백그라운드로 옮기는
것만으로는 캐시 읽기가 잠금에 막힌다. 스냅샷 상태 잠금과 계정별 작업 직렬화를
분리해야 한다. 같은 계정의 중복 갱신은 합치고, 동일 Telegram DB를 여러 워커가
동시에 여는 것은 방지한다. query의 대상 계정 탐색도 무관한 계정 잠금을 피한다.

갱신 중 정렬·offset 변경으로 페이지가 누락되지 않도록 스냅샷 버전을 커서에
연결하거나 일관된 스냅샷 단위로 교체한다. 방 선택·검색 위치·초안은 ID로 유지한다.

### 2. 목록 스냅샷 암호화 저장

방 ID, 메신저 원래 이름, 최근 시각·미리보기, 갱신 시각을 계정별로 기존
SQLCipher 저장 경계 안에 저장한다. 재부팅 후에도 네트워크보다 먼저 표시한다.
계정 제거 시 캐시도 삭제한다. 캐시 표시와 현재 전송 권한은 별도 상태로 관리한다.
오래된 스냅샷만으로 authenticated를 새로 판정하면 안 된다. 기존 실패 시
전송 차단과 중복 전송 방지도 유지한다.

### 3. Slack 반복 요청 줄이기

계정별 이름 캐시를 유지하고 만료·변경 시 갱신한다. 같은 이름에 대한 진행 중
요청도 공유한다. 최근 메시지는 캐시로 먼저 표시하고 변경된 방 중심으로 갱신한다.
장기적으로 수신 이벤트 반영을 검토하되, 현재 계정 구현에는 해당 경로가 없다.
bulk API 전환 시 현재 개인 세션의 지원·권한을 별도로 확인해야 한다.

전체 방·원래 이름·최신순 정렬 요구를 유지해야 하므로 history를 무조건 생략하는
방식은 적합하지 않다. 동시 요청 수만 늘리면 요청 총량은 그대로이며 제한에
걸릴 수 있으므로 우선 캐시와 화면 표시 의존 관계를 수정한다.

### 4. 조회 중과 빈 결과 구분

기존 목록을 유지하며 갱신 중임만 짧게 표시한다. 캐시가 없으면
“대화 불러오는 중…”을 표시한다. 이는 혼란을 줄이며 원격 시간 단축과는 별개다.

## 구현 후 검증 기준

- 느린 Slack 없이 완료된 Telegram을 먼저 표시하고 사용할 수 있다.
- 캐시 읽기는 원격 작업 완료나 원격 작업의 mutex를 기다리지 않는다.
- 재시작 후 목록 복원과 새 데이터 갱신이 모두 동작한다.
- 다중 TUI·재연결 시 계정별 갱신이 중복되지 않는다.
- 페이지 누락·방 중복·선택 이동·초안 소실이 없다.
- 실패한 계정은 캐시만으로 전송 권한을 복구하지 않는다.
- 지연 제어 테스트 워커로 순서를 검증하고 설치된 TUI에서 첫 화면,
  첫 방, 전체 갱신 완료 시간을 따로 측정한다.

캐시 실험 3ms와 헤더 측정 583ms를 근거로, 캐시 있는 실행의 방 표시를
1초 이내로 줄이는 것을 목표로 삼을 수 있다. 캐시 없는 실행도 빠른 계정부터
표시해 사용 시작을 앞당길 수 있다. 둘 다 구현 후 실제 TUI 재측정이 필요하다.
