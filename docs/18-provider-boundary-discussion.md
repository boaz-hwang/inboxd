# Rust–TS 제공자 경계 비교

2026-09-19. 논의용 제안. 책임 이전을 승인하거나 구현한 문서가 아니다.
현재 리팩토링은 기존 Rust 정책 / TS SDK 호출 경계를 유지한다.

## 판단

현재는 제공자별 **의미와 조회 계획을 Rust에 유지**할 근거가 더 강하다.
Rust는 저장소, 전송 기록, 작업 예산과 같은 상태를 이미 소유한다.
조회 계획을 알면 페이지 사이에 다른 작업을 처리하고 수집 진행을 저장할 수 있다.
반면 SDK 인자나 원시 필드명 자체를 Rust에 노출하는 가치는 제한적이다.
TS가 원시 표현을 명시적인 내부 계약으로 변환하되, 커서 종료·변경 감지·ACK 등
Rust 판단에 필요한 증거를 잃지 않는 경계를 권한다.

정책 집중의 이점은 Rust 언어만의 이점이 아니다. TS에서도 같은 설계가 가능하다.
이번 판단은 현재 상태 소유권과 테스트 위치에 근거한다. 언어별 개발 시간이나
운영 장애 감소를 측정한 결과는 아니다.

## 변경 빈도에 관해 알 수 있는 것

- 계정 어댑터의 저장소 이력은 최근 도입에 집중돼 있다. 운영 기간이 짧아
  연간 API 변경 횟수, 장애 확률, 평균 대응 시간을 신뢰성 있게 추정할 수 없다.
- TDLib 공식 문서는 JSON 연결 인터페이스의 같은 major 호환성과 실제 API의
  호환성을 구분한다. 실제 API는 minor/patch에서도 다를 수 있다. 현재 TDLib와
  tdl 버전을 고정했으므로 로컬 SDK 업그레이드 시점은 통제할 수 있지만, 서버
  정책·호환 지원이 영원히 유지된다는 뜻은 아니다.
  [TDLib 문서](https://core.telegram.org/tdlib/docs/)
- Slack에는 history/replies 호출 제한처럼 결과 JSON보다 실행 정책이 달라지는
  변경 사례가 있다. 이 공지는 특정 상용 배포 앱 등이 대상이며, 현재 개인 세션에
  같은 제한이 적용된다고 주장하지 않는다. 공개 변경 공지의 수를 우리가 사용하는
  API의 변경 확률로 환산해서도 안 된다.
  [Slack 변경 공지](https://docs.slack.dev/changelog/2025/06/03/rate-limits-clarity/)
- 개인 Slack의 client.counts와 Kakao SDK 동작은 저장소의 실제 관측/패치에 기대는
  부분이 있다. 이 경로의 안정성 계약이나 변경 주기를 확인한 자료는 없다.
  SDK 버전 고정은 서버 변화까지 고정하지 않는다.
  [API 관측](14-api-call-audit.md), [SDK 패치](../patches/agent-messenger@2.37.1.patch)

## 변경 종류별 비교

| 변경 | Rust가 알아야 할 내용 | TS에서 흡수할 내용 | 경계 비용 |
| --- | --- | --- | --- |
| 필드명·인자·SDK 함수 변경 | 기존 의미가 같으면 변경 불필요 | 원시 표현과 내부 타입 변환 | raw 응답이 Rust에 퍼지면 양쪽 수정 |
| 커서/종료 조건 변경 | 수집 완료 근거, 다음 작업, 중복·순환 방지 | 토큰 표현, SDK 인자 | 단순 next_cursor 하나로 의미를 숨기면 누락 위험 |
| 호출 제한 | 전체 계정 예산, 기다리는 작업, 재개 시점 | 제공자 오류와 Retry-After 추출 | TS 내부 재시도는 중앙 스케줄링을 우회할 수 있음 |
| 수정·삭제 감지 변경 | cache/index 무효화, 변경 검증 범위 | 이벤트 형식과 원시 필드 변환 | 공통 메시지로만 축약하면 중요한 증거 손실 |
| 로그인·세션 변경 | 인증 가능/실패 상태 | 로그인과 SDK 세션 상태 | Rust에 로그인 순서를 복제할 이점 작음 |
| 새 제품 기능 | 검색 범위, 수집·전송 정책 | 새 SDK primitive 구현 | 필요한 기능에 따라 양쪽 수정이 정상적일 수 있음 |

## 비교할 세 안

1. **원시 응답까지 Rust가 소비:** 가장 직접적이며 제공자별 최적화·테스트가 편하다.
   응답 표현 변경이 Rust로 전파되고 스키마 해석이 양쪽에 생길 수 있다.
2. **TS가 의미 있는 primitive 계약으로 변환, Rust가 계획:** 원시 변화의 일부를
   TS에서 흡수하며 정책은 중앙화한다. 계약 설계/검증 비용이 들고, 제공자 고유
   증거를 모두 공통 타입으로 억지 통합하면 오히려 정확성이 떨어진다.
3. **TS가 검색·캐시·이력 순회를 통째로 수행:** 제공자 기능 개발을 한 언어에서
   하기 쉽다. Rust는 긴 작업의 중간 진행을 통제하기 어려우며, 이를 해결하려면
   TS 작업도 단계·취소·진행 상태를 노출해야 하므로 경계가 다시 복잡해진다.

현재는 2번을 기준으로 하되, 가치 있는 제공자 고유 정보를 타입으로 유지하는
안을 선호한다. 기능/성능 이득 없이 기존 코드를 이동할 필요는 없다.

## 실제로 비용을 판단하는 방법

기대 유지 비용은 대략 `표현 변경 횟수 × 표현 변경 대응 비용 + 의미 변경 횟수 ×
정책/검증 변경 비용 + 계약 유지 비용`으로 볼 수 있다. 숫자는 아직 없다.
향후 실제 수정에서 TS만 변경했는지, Rust도 변경했는지, 테스트·배포까지 걸린 시간과
결함을 기록하면 경계를 옮길 근거가 생긴다. 요청 빈도와 API 변경 빈도는 다르다.

현재 제품은 Rust 데몬과 TS 실행 파일을 함께 패키징한다. TS만 독립 배포하는
운영상 이점을 이미 누리는 구조가 아니다. 원시 필드 변경이 Rust까지 전파되는
개발 비용과 전체 패키지를 배포하는 운영 비용은 분리해 평가해야 한다.

검색·전송 통합은 별도 [검토 문서](17-unified-routes-review.md)에 있다. 공통 검색
저장소와 작업 스케줄러를 사용할수록 Rust가 수집 계획·증거를 아는 가치는 커진다.
