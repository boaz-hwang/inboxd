# 과거 메신저 대화의 개인화 학습 데이터·파이프라인 설계

작성일: 2026-10-01 · 통합 갱신일: 2026-10-04

**최신 결과:** 메모리 개선 후 4K·535회 본학습과 최종 96건 비교 평가를 끝냈다. 본학습 최대 MLX 메모리 약 29.99GB, 추가 스왑 0, 학습·저장본 검증 중 OS 압력 표본 1,377개 모두 정상이다. 실제 최종 48건의 명확한 의미 오류는 기본 모델 25건→선택 후보 12건으로 줄었지만, 합성 평가 유용성은 하락했고 역할·동의 오류가 남았다. **이번 어댑터는 적용하지 않고 기존 기본 모델을 유지한다.** 메모리 개선 경로를 소스와 설치본에 반영했고 관련 테스트 71개를 통과했다. 상세 결과는 18.3~18.6절에 기록한다.

**2026-10-05 검토 범위 정정:** 3,086건은 후보 전체이며, 의미 판정 장부에서 확인되는 완료 범위는 1,117건이다. 그중 승인 481·보류 603·제외 33건, 이후 추가 보류 10건을 반영해 실제 471건을 학습했다. 나머지 1,969건이 모두 품질 탈락한 것은 아니다. 전체 후보 검토를 마치기 전에 535건 학습 실험으로 넘어갔으며, 전체 후보 검토 완료와 실험 완료를 구분한다. 아래 18.7절에 근거와 정리 내역을 남긴다.

**2026-10-06 후속:** 원래 3,086건의 전체 판정과 승인된 실제 답장 1,374건의 Granite 한 epoch 학습을 마쳤다. 학습 전후 108개 답장을 블라인드로 판정했으며, 손실 감소와 일부 말투 개선에도 실사용 유용성은 제한적이었다. 전체 후보 집계·원문 보존·평가 분할·자원과 품질 결과는 [30번 문서](30-granite-fullpool-training.md)에 별도로 기록한다. 이 문서의 이전 Qwen 학습 결과와 검토 범위 정정은 당시 이력으로 보존한다.

상태: **4K 데이터 확대·메모리 개선·학습·평가·원인 분석 완료, 품질 기준 미달로 운영 기본 모델 유지**. 사용자의 원래 요청과 선별 원칙에 데이터 추출 계약, 실행 단계, 학습·평가 계획을 통합했다. 첫 실험은 242건을 검토하고 체크포인트를 비교했으나, 자원 초과와 거절을 승인으로 뒤집는 회귀 때문에 적용하지 않았다(13장). 이후 15장의 계획으로 정상 학습과 별도 품질 평가를 마쳤지만 독립 평가와 거절 보존 기준을 충족하지 못해 적용하지 않았다. 사용자가 카카오톡 중심의 최대한의 기록 확보, 검수 후 재학습, 개선 여부 확인과 조건부 어댑터 적용 및 추가 개선을 요청하여 16장의 후속 작업과 18장의 메모리 개선·최종 평가를 완료했다.

**학습 실행 정책:** 매일 오전 4시 자동 학습 일정은 사용자 요청으로 삭제했으며 복원하지 않는다. 향후 학습 필요성을 먼저 판단하고 필요한 경우에만 실행하는 구조로 변경할 계획이다. 필요성 판단 로직은 아직 미구현이며, 기존 데이터 수·분할 조건은 실행 준비 조건일 뿐 필요성 판단이 아니다. 현재는 사용자가 직접 지시한 4K 데이터 검수·메모리 시험·학습만 계속한다.

**학습 전 메모리 확보:** 사용자 요청에 따라 모든 시뮬레이터·에뮬레이터를 종료하고 실행 중인 기기가 없는지 확인한다. 학습 직전 다시 확인한 뒤 추천 데몬을 일시 정지하고 메모리 상태가 안정됐을 때 실제 승인 데이터로 4K 메모리 시험을 진행한다. 단순 종료 여부를 메모리 시험 통과로 간주하지 않는다.

**아래 자원 시험 요약은 구현 수정 전의 이력이다.** 당시의 중단·미착수 기록을 보존하며 최신 성공 결과와 적용 판단은 문서 첫 문단 및 18.3절 이후를 따른다.

**2026-10-04 데이터 확정:** 신규 검토 묶음 처리를 마친 뒤 실제 대화 승인 후보 481건을 원문과 다시 대조했다. 학습 75방과 기존 검증 4방에서 원문 10,921건·기존 생략 메타데이터 47건이 모두 동결 자료와 일치했다. 실제·합성 학습 후보와 검증·최종 평가 자료의 교차 중복 검사에서 정확/근접 본문·공유 원천·동일 입력 충돌은 없었다. 학습 후보 전체에 형식 조건을 검사하고 해당 정답 106개만 추가로 읽어 장문·여러 완결문장·지도공유 카드 형식 9개를 보류했다. 학습 내부 근접 중복 77쌍 중 기능상 추가 검토가 필요한 15쌍을 확인해 같은 맥락의 반복 답장 1개를 보류했다. 모든 의미상 유사표현을 제거했다는 뜻은 아니다. 최종 학습은 **실제 471개(74방) + 합성 64개 = 535개**, 검증은 기존 **실제 30개 + 합성 16개 = 46개**로 봉인했다. 의미 판정 출처는 사용자가 위임한 `agent_delegated`다. 전체 학습·검증의 정답 및 종료 토큰 상한은 66, 실제 학습 최대 입력은 3,885·전체는 3,904토큰이다. 사전 코드 검사 13개를 통과했고, 대체된 검토용 메모리 프로세스 4개를 정상 종료했다. 첫 실제 6개 사례의 메모리 시험은 사전 안정 조건을 통과했으나, 시작 18.3초에 OS 메모리 압력 경고로 첫 업데이트 전에 중단됐다. 성공한 학습 업데이트는 0회이며 본학습도 시작하지 않았다. 미사용 캐시를 1GiB로 제한한 별도 시험도 17.6초에 첫 업데이트 중 메모리 압력 경고로 중단됐다. 이때 자동 데몬 복구와 암호화 스키마 7 확인은 통과했다. 추가로 작업 없는 Gradle 데몬 1개를 정상 종료한 뒤 MLX의 비동기 작업 메모리 가이드라인을 20GiB로 낮춰 시험했다. 2,305·2,465·2,753 패딩 길이의 첫 3회는 유한한 손실·기울기·업데이트로 완료했지만, 네 번째 3,137 길이에서 메모리 압력 경고로 중단됐다. 성공한 3회의 MLX 최대 활성 메모리는 각각 25.92·27.39·30.00GB였다. 20GiB는 엄격한 할당 상한이 아니며, 전체 6개 길이·18회 시험과 본학습은 아직 통과하지 못했다. 데몬 복구·스키마 7 확인은 통과했다. 추가 메모리 확보와 계산 그래프의 메모리 점유 원인을 점검하고 있다.

**추가 메모리 시험:** 계산 그래프의 실행 순서를 조정하는 `MLX_BFS_MAX_WIDTH=4`를 적용한 별도 시험도 3/18회 완료 후 네 번째 긴 사례에서 OS 메모리 압력 경고로 중단됐다. 첫 3회의 손실·기울기 크기·업데이트 크기는 직전 시험과 같았고, 최대 활성 메모리는 약 0.84~1.00GB 줄었지만 충분하지 않았다. 이 비교는 전체 기울기 배열의 동일성을 검증한 것은 아니다. 자동 데몬 복구와 암호화 스키마 7 확인은 통과했다. 다음으로 학습하지 않는 앞쪽 레이어의 계산을 순서대로 끝내는 방식을 작은 Qwen3.5 CPU 모델로 검사했다. 손실·전체 학습 기울기·Adam 1회 업데이트·옵티마이저 상태가 모두 같았으며, 그러나 이 방식을 실제 모델에 적용한 시험은 레이어 구성 검증을 통과한 뒤 첫 업데이트 전 메모리 압력 경고로 중단됐다(0/18회). 따라서 이 방식의 메모리 개선은 입증되지 않았다. 데몬 복구·독립 스키마 7 확인은 통과했다. 고정된 앞쪽 레이어를 기울기 계산 밖으로 옮긴 별도 방식도 CPU에서 연속 두 업데이트와 중간 평가가 원래 방식과 일치했다. 실제 시험에서는 3,137 패딩 길이까지 4/18회 완료하고 다섯 번째 긴 사례에서 메모리 압력 경고로 중단됐다. 첫 3회의 최대 활성 메모리는 기존 BFS4 시험과 같아 절감 효과는 확인되지 않았다. OS 상태도 달랐으므로 4회까지 진행한 결과를 코드 개선의 효과로 단정하지 않는다. 이 중단은 사전에 정한 ‘메모리 압력 정상 상태만 허용’ 기준에 따른 것이며, 이번 실제 시험들에서 메모리 할당 실패가 발생했다는 뜻은 아니다. 본학습과 새 어댑터 적용은 아직 시작하지 않았다.

**구현 수정 전 자원 중단 이력:** 정상 압력만 허용한 기존 시험과 구분해, 짧은 경고만 허용하는 별도 진단을 사전에 정해 실행했다. 경고 연속 5초·누적 10초, 시스템 wired 메모리 38GiB, 회수 가능성 지표 2GiB, 추가 스왑 1GiB를 한도로 두고 1초 간격으로 측정했다. 이 진단도 4/18회 완료 후 다섯 번째 사례에서 압력 값 4(critical)가 관측되어 중단됐다. 같은 최종 표본에서 wired 41.22GB, 회수 가능성 지표 1.64GB, 추가 스왑 1.31GB로 해당 한도도 넘었다. 첫 고정 prefix 계산의 최대 활성 메모리는 약 5.76GB였고 첫 업데이트 완료 시 약 25.08GB로 증가해, 큰 메모리 증가는 prefix 완료 이후에 관측됐다. Metal 할당 실패를 관측한 것은 아니지만 현재 자원 상태로는 학습을 지속할 수 있다는 근거가 없다. 데몬 복구와 별도 암호화 스키마 7 확인을 마쳤으며 어댑터는 생성·적용하지 않았다. 다른 앱 정리 등 실제 여유 메모리 상태가 바뀌기 전까지 추가 GPU 시험과 CPU 최적화 반복을 중단한다. 자원이 확보되면 원래 정상 압력 기준으로 다시 시험하며, 이번 경고 허용 진단을 본학습의 기본 정책으로 바꾸지 않는다. 본학습은 아직 시작하지 않았다.

**이번 본학습 계획:** 4K 메모리 시험을 통과하면 535개를 1회 순회하고 134·268·402·535회 저장본을 비교한다. 마지막 535회 가중치는 검증 선택 전에 별도 번호 파일로 보존한다. 이전 실험의 반복 증가에 따른 품질 저하를 반영한 설정이며, 시간 예산은 실제 메모리 시험의 속도로 확정한다. 최종 평가 기준과 운영 입력 형식은 유지한다.

**모델·메모리 원인 재검토:** 후속 사용자 요청에 따라 소스·공식 모델 설정·작은 합성 CPU 계산을 분석했다(17장). 현재 9B가 이 서비스에 최선이라는 모델 간 비교 근거는 없다. 긴 입력의 recurrent state를 미분하는 학습 경로가 가장 유력한 메모리 병목이며, Qwen3.5-4B도 해당 상태의 차원은 같다. 내부 연산의 컴파일만 켜는 방식은 작은 CPU 대조에서 계산 그래프를 줄이지 못했다. 이 분석은 새 GPU 시험이나 본학습 재개가 아니며, 운영 모델·학습 입력·설치 라이브러리는 유지한다.

**사용자 지시에 따른 구현 재개:** 사용자가 메모리 병목부터 해결하고 학습을 끝까지 진행하도록 지시했다. 기존 9B의 전체 문맥 기울기를 보존하면서 recurrence backward의 동시 메모리를 줄이는 구현과 독립 CPU 검증을 먼저 진행한다. 검증 후 원래 정상 압력 기준으로 실제 4K 시험을 재실행하고 통과하면 535개 본학습·품질 평가로 이어간다. 앞선 실패 기록과 최종 평가 격리는 유지하며, 재개 지시 자체를 메모리 문제 해결이나 학습 완료로 기록하지 않는다.

**재개 후 첫 결과:** 구간별 VJP와 독립 값 복사를 사용하는 후보는 작은 CPU 모델의 전체 62개 기울기·연속 Adam 두 번·중간 검증에서 기존 결과와 일치했다. 그러나 실제 동일 6개/18회 시험은 22.989초에 메모리 압력 2로 첫 업데이트 전에 중단됐다. 이때 시스템 wired 메모리는 39.055GB였다. CPU 계산 그래프 감소를 실제 GPU 메모리 개선으로 해석하지 않는다. 데몬·스키마 7 복구를 확인했고, 다음 진단에는 구간별 계측과 12GiB 활성 메모리 조기 중단 조건을 추가한다. 이 조기 한도는 원인 진단용이며 본학습의 새 기준이 아니다. 별도로 일반 attention 구조의 Qwen3-4B 후보 비교를 준비하되 운영 모델은 아직 바꾸지 않았다.

| 개발 비교 | 선택된 152회 후보는 의미 오류 8→4건으로 줄었지만 유용성이 기본 모델보다 낮아 적용하지 않음. 새 마지막 지시문 실험도 악화되어 채택하지 않음. |
| 4K 확대·학습 | 실제 471 + 합성 64 = 535개로 1회 순회 완료. C16 메모리 개선 후 최대 MLX 29.99GB, 추가 스왑 0. 개발 24건 비교로 268회 저장본 선택. |
| 최종 평가·운영 | 실제 48 + 합성 48개 × 3모델의 출력 288개 블라인드 판정 완료. 실제·합성 최종 기준 및 관측 회귀 기준 미달로 후보 미적용. 활성 어댑터 없음. |

## 1. 사용자의 원래 요청

카카오톡·텔레그램에 이미 쌓인 대화에서 **‘이전 맥락 → 내가 실제로 보낸 답장’**을 적절한 단위로 추출해, 추천 정확도를 높일 파인튜닝 데이터로 활용한다.

이를 위해 내 발신이 없는 방의 처리 등 **대상 선별·대화 분할·품질 검토 기준을 먼저 설계하고, 구현 전에 검토할 수 있게 제안한다.**

배경은 추천 답장에서 발생한 역할 반전이다. 상대가 한 행동을 내가 한 것처럼 쓰는 문제를 줄이고, 내 말투와 답장 방식에 맞는 추천을 만드는 것이 목적이다. 대화량이나 학습 완료 자체를 개선의 증거로 삼지 않는다.

## 2. 학습 단위와 전체 흐름

학습 단위는 **‘내가 답장한 한 번의 상황’**이다.

- 입력: 답장 전에 추천 모델이 볼 수 있었던 대화와 발신자·답장 관계.
- 정답: 내가 실제로 보낸 답장 턴. 여러 메시지로 나눠 보냈다면 조건에 따라 하나로 묶는다.
- 출처: 원본 메시지, 수집 상태, 연결 근거와 변환 규칙 버전.

```text
저장된 과거 대화 + 필요 범위의 추가 수집
  → owner 전용 후보 추출
  → 답장 턴 구성·출처 중복 제거
  → 운영과 같은 입력 구성·품질 선별
  → 사용자 또는 명시적으로 위임받은 검토자의 의미 검토
  → 학습·검증·평가 데이터 분리·동결
  → LoRA 학습·비교 평가
  → 결과 검토 후 수동 적용·롤백

Inboxd 응답 세션의 실제 전송 기록
  → 같은 입력 구성·선별·검토·분할 과정으로 합류
```

과거 대화로 초기 데이터를 확보하고, 이후 사용자가 작성한 새 답장으로 보충하는 흐름을 목표로 한다. 데이터 준비와 학습은 오프라인 작업으로 수행하며, 실시간 추천은 현재의 단일 생성 호출 구조를 유지한다.

새 어댑터를 적용하면 실제 추천에 사용하는 조합이 `기본 모델 + 새 개인화 가중치`로 바뀐다. 학습, 평가, 적용은 구분된 단계다.

## 3. 채팅방 선별

채팅방 전체를 성급하게 제외하기보다 **확인된 수집 구간과 내 참여 여부**를 기준으로 판단한다.

| 상태 | 처리 |
|---|---|
| 수집된 구간에 내 발신이 없음 | 해당 구간에서 학습 사례를 만들지 않는다. |
| 과거 대화가 일부만 수집됨 | 수집 부족으로 표시한다. 내 발신이 없는 방으로 단정하지 않는다. |
| 내가 참여한 1:1 대화 | 답장 후보를 추출한다. |
| 내가 참여한 단톡방 | 발신자와 답장 대상이 명확한 사례를 추출한다. |
| 내 계정·발신자를 식별할 수 없음 | 식별이 해결될 때까지 보류한다. |

단톡방도 처음부터 후보에 포함한다. 방 종류보다 개별 답장의 연결 관계가 중요하다. 관측된 발신자가 두 명이라는 이유만으로 1:1방으로 판단하지 않는다. 방 종류를 확인할 수 없으면 미확인 상태를 유지한다.

내가 보내지 않은 타인의 메시지는 맥락으로만 사용한다. 내 발신이 없는 방의 대화를 타인의 답장으로 대체해 개인화 정답으로 만들지 않는다.

수집 현황만으로 추가 수집이 유일한 병목이라고 단정하지 않는다. 먼저 저장된 데이터의 후보 수·탈락 사유·토큰 분포를 확인하고, 플랫폼별 대표 방에서 과거 기록의 도달 기간·속도·제한을 측정한다. 수집 범위 근거를 남기는 `sync.backfill`을 우선 검토하며, 방별 중단·재개와 `sync_limits` 기록을 설계한다. `account.messages`로 페이지를 읽어 저장한 사실만으로 해당 기간의 수집 완전성을 주장하지 않는다.

기본 대상은 카카오톡·텔레그램이며 Slack은 명시적으로 선택할 때만 포함한다. 포함하면 플랫폼별 말투와 평가 결과를 따로 확인한다. 추가 수집의 대상 방·기간·페이지 예산은 실행 전에 정하고, 중단 후에는 데몬의 실제 진행 상태와 저장된 체크포인트를 확인해 재개한다. 기존 동기화의 범위는 [실시간 동기화 문서](19-live-synchronization.md)를 참고한다.

## 4. 내 답장 턴 추출

상대 발언에 이어 내가 응답한 지점을 찾고, 연달아 나눠 보낸 메시지를 하나의 답장으로 묶는다.

아래는 구조 설명용 가상 예시다.

```text
상대: 제가 앱을 하나 만들었어요.
나: 직접 만드신 거예요?
나: 대단하시네요 ㅎㅎ

입력: 상대의 발언과 그 이전 맥락
정답: 직접 만드신 거예요?
      대단하시네요 ㅎㅎ
```

묶음의 판단 요소는 같은 발신자, 같은 답장 대상, 다른 사람의 개입 여부, 전송 간격이다. 주제가 바뀌거나 다른 메시지에 답한 경우에는 분리한다.

시간 간격은 경계 판단을 돕는 신호로 사용한다. 실제 플랫폼별 메시지 간격과 검토 표본을 확인해 설정값을 정한다. 앞선 초안의 ‘2분 이내 묶기’, ‘6시간 공백으로 자르기’는 이 설계의 확정 기준이 아니다.

내가 새 대화를 시작한 메시지는 별도 분류한다. 첫 학습 대상은 현재 추천 기능에 맞는 **상대 발언에 대한 답장**이다.

과거 후보와 Inboxd 응답 세션 후보가 같은 전송을 가리키면, 당시 입력 스냅샷이 확인되는 세션 후보를 우선한다. 중복 판정은 플랫폼·계정·방·원본 메시지 ID와 전송 영수증의 연결을 사용한다. 본문이 같다는 이유만으로 같은 전송으로 간주하지 않는다. 후보에 여러 정답 메시지가 묶여 있으면 메시지별로 중복과 작성 출처를 확인한다.

추천을 수정 없이 보냈다고 확인된 메시지는 개인화 정답에서 제외한다. 출처 기록이 없으면 `unknown`으로 남기며 직접 작성했다고 단정하지 않는다. 세션 경로에서 학습 부적격으로 제외된 추천문이 과거 후보 경로로 다시 들어오는 것도 막는다.

## 5. 답장 직전의 입력 구성

답장 이전의 대화에서 최근 발언과 필요한 참조 원문을 가져온다. 발신자를 `나`, `상대 A`, `상대 B`처럼 일관되게 구분하고 명시적인 답장 관계를 보존한다.

학습과 실제 추천은 **같은 맥락 선택 방식과 입력 형식**을 사용한다. 학습 때만 제공되는 정보에 의존하지 않도록 다음 경계를 지킨다.

- 내 답장과 그 이후 대화는 입력에 포함하지 않는다.
- 답장 후 수정된 메시지는 당시 원문을 복원할 수 있을 때 사용한다.
- 내 답장의 참조정보는 연결 관계를 검토하는 데 사용한다. 추천 시점에 알 수 없던 대상 정보를 입력에 추가하지 않는다.
- 정답 내용에서 정보를 뽑아 과거 입력이나 요약을 보강하지 않는다.
- 입력 길이를 줄이더라도 답장 대상과 필수 맥락을 보존한다. 그게 불가능하면 보류한다.
- 정답이 잘려 나가는 사례를 학습에 넣지 않는다.

맥락 구성은 저장소의 읽기 전용 `context_snapshot(chat, before)` 함수로 분리해 운영과 과거 후보 추출이 공유한다. 현재 운영의 최근 40개 메시지와 마지막 메시지의 답장 조상 최대 8개 선택 규칙을 출발점으로 삼는다. `before`는 정답의 첫 메시지 직전 경계를 나타내며, 참조 원문 조회에도 같은 시점 제한을 적용한다. 같은 시각의 메시지 순서를 신뢰할 수 없는 사례는 보류한다. 기존 `prepare`의 추천 작업 생성·갱신 같은 부수 효과는 추출 경로에 포함하지 않는다.

현재 모델은 마지막 상대 발언에 답하도록 지시받는다. 따라서 **학습 답장의 대상과 모델 입력의 답장 대상이 일치하는지** 확인한다. 단톡방에서 내 답장이 더 앞선 사람의 발언을 참조하면, 명시적인 참조가 있더라도 `reply_target_mismatch`로 보류한다. 현재 추천 입력으로 같은 대상을 재현할 수 있어야 학습 후보가 된다.

`incoming_message_ids`는 운영에서 읽음 커서와 미읽음 기록을 바탕으로 구성된다. 이를 과거의 ‘직전 내 발신 이후 상대 메시지’로 대신 채우지 않는다. 세션 후보는 당시 저장된 `source_json` 등에서 복원하고, 과거 후보는 `unseen_state: unknown`으로 보존한다. 모델 입력에서도 미확인 상태를 유지한다. 현재 작업 트리의 `compile_prompt`는 ID 목록이 없거나 `null`이면 `unseen: null`, 명시적인 빈 목록이면 확인된 미읽음 메시지가 없는 상태로 구분하며, 입력 버전은 `reply-v4`다. v4는 생성 입력의 반복 메타데이터를 고정 필드 배열로 표현하고 메시지 ID를 입력 내부 별칭으로 바꾼다. 원본 발신자 ID·절대 시각·본문·역할·답장 관계·미확인/거짓 구분은 유지한다. 저장소 원본과 출처 ID는 바꾸지 않는다.

수정 상태도 `verified_unchanged / edited_after_target / unknown`으로 구분한다. `edited_at`이 없다는 사실은 수정되지 않았다는 증거가 아니다. 당시 본문을 확인할 수 없는 사례는 표시해 별도 검토하고, 정확한 시점 재현을 평가할 전용 데이터에는 넣지 않는다. 현재 본문이 답장 뒤 수정됐다고 확인되면 당시 원문을 복원하기 전까지 보류한다.

학습 점수는 마지막 정답인 내 답장에만 계산하고, 이전 대화는 입력으로 사용한다. 입력·정답을 분리하고 정답 부분에만 학습 손실을 계산하는 구성은 [Hugging Face의 SFT 문서](https://huggingface.co/docs/trl/sft_trainer#train-on-completion-only)에서 설명하는 방식과 같다. 이는 설계 원칙의 근거이며 현재 MLX 학습 도구를 TRL로 교체한다는 제안은 아니다.

## 6. 품질 선별

검토 질문은 **‘모델에게 제공할 맥락으로 이 답장을 추천해도 되는가?’**다. 실제 사용자가 보낸 말이라는 사실만으로 모델의 추천 정답으로 확정하지 않는다.

| 사례 | 제안 처리 |
|---|---|
| 상대의 설명에 대한 감사·질문·자연스러운 반응 | 학습 후보 |
| 이전에 밝힌 내 결정이나 의견을 이어가는 답장 | 학습 후보 |
| 단톡방에서 누구에게 답했는지 모호함 | 보류 |
| 사진·통화·링크 내용을 알아야 이해되는 답장 | 필요한 내용이 입력에 없으면 보류 |
| 입력에 근거가 없는 “입금했습니다”, “내일 가능합니다” | 보류 |
| 삭제·수집 누락으로 대화가 끊김 | 보류 |
| 시스템 알림·자동 발송·중복 수집 | 제외 |
| “네”, “ㅋㅋ” 같은 짧은 답장 | 유지하되 편중을 제한 |

사진이나 링크가 등장했다는 사실만으로 전부 제외하지는 않는다. 답장을 이해하거나 추천하는 데 그 내용이 필요한지 구분한다. 외부 행동을 실제로 했더라도 모델 입력에서 알 수 없다면 그 완료 보고는 추천 학습 대상으로 보류한다.

형식과 누락은 코드로 검사한다. 의미가 애매한 사례는 근거와 함께 검토 대상으로 분리한다. 로컬 모델은 필요할 때 분류를 보조할 수 있지만, 그 판단을 자동으로 정답 처리하지 않는다. 이 보조 분류는 오프라인 데이터 준비 단계이며 추천 생성 뒤에 검증 모델을 다시 추가하는 구조가 아니다.

정답은 사용자 원문을 보존한다. 예를 들어 모델이 “입금했습니다”를 “확인해보겠습니다”로 고쳐 학습 정답으로 만들지 않는다.

**답장하지 않았다는 사실은 부정 학습의 정답으로 사용하지 않는다.** 읽지 않았거나 다른 경로로 응답했을 수도 있다. 직접 답장을 작성했다는 이유만으로 당시 제시된 추천을 잘못된 답장으로 라벨링하지도 않는다.

자동 선별 결과에는 사유 코드를 남긴다. 아래는 선별 계약이며 구현·검증 상태는 13장에서 관리한다.

| 사유 코드 | 처리 |
|---|---|
| `self_identity_unknown`, `preflight_not_ready` | 발신자·필수 맥락 문제를 해결할 때까지 보류. 구체적인 하위 사유도 기록 |
| `reply_target_mismatch` | 모델이 답할 대상과 실제 답장 대상이 다르면 보류 |
| `unchanged_model_suggestion`, `duplicate_of_session_candidate` | 확인된 추천 원문·중복 전송은 제외 |
| `non_text_target` | 빈 본문·서비스 이벤트·텍스트 없는 자리표시자는 제외 |
| `over_token_budget` | 실제 토크나이저로 센 입력+정답이 학습 한도를 넘으면 해당 사례만 보류 |
| `target_exceeds_generation_limit` | 정답이 운영 생성 한도를 넘으면 보류. 현재 한도는 192토큰 |
| `context_edited_after_target` | 당시 원문을 복원하기 전까지 보류 |
| `context_edit_unknown`, `coverage_unverified`, `authorship_unknown` | 확인되지 않은 근거를 표시하고 별도 검토 |
| `group_without_explicit_reply`, `long_reply_gap`, `external_content_likely` | 검토 필요 표시. 이것만으로 의미상 부적합을 확정하지 않음 |

길이가 긴 사례를 앞단에서 보류하더라도 학습기의 최종 길이 검사는 유지한다. 검사 누락이나 규칙 불일치로 정답이 잘리는 실행은 중단해야 한다. 사유별·플랫폼별·방별 건수와 함께 입력·정답 토큰 분포를 보고한다.

## 7. 검토 가능한 사례 목록

| 항목 | 내용 |
|---|---|
| 입력·정답 | 실제 학습에 들어갈 이전 대화와 내 답장 |
| 출처 | 플랫폼, 계정, 채팅방, 원본 메시지 ID와 시각 |
| 작성 출처 | 과거 대화·응답 세션 구분, 직접 작성·추천 수정·추천 그대로 전송·미확인 |
| 연결 근거 | 직접 답장 참조, 연속 대화 등 |
| 수집 상태 | 관련 구간의 수집 범위, 누락·수정·읽음 상태의 확인 여부 |
| 품질 판정 | 후보·보류·제외와 구체적인 이유 |
| 버전 | 원문과 변환 규칙의 변경을 확인할 정보 |
| 검토 상태 | 미검토·승인·보류·제외 |

후보 판정과 검토 승인을 분리해서 기록한다. 형식 검사를 통과했다는 의미와 검토자가 의미를 확인했다는 의미를 섞지 않는다. 사용자는 첫 10건을 제안대로 승인한 뒤, 앞으로의 모든 제안 판단을 에이전트에 위임했다. 이후 판정에는 `agent_delegated`와 위임 근거를 기록하며 사용자가 각 원문을 직접 검토했다고 표시하지 않는다. 미확인 작성 출처·수정 이력·수집 상태는 위임 승인 후에도 미확인으로 남는다.

첫 검토는 서로 다른 방·플랫폼·답장 유형에서 뽑은 **약 100개**를 시작점으로 제안한다. 품질을 보장하는 표본 수나 학습 최소량이 아니라 추출 규칙을 점검하기 위한 초안이다.

검토 결과로 규칙을 수정한 뒤, 승인된 기준에 따라 일괄 선별하고 애매한 사례를 추가 검토한다. 이 일괄 선별 방식은 제안이며 현재의 건별 검토 절차가 이미 바뀌었다는 뜻은 아니다.

특정 상대와의 대화, 반복 인사, 짧은 반응이 대부분을 차지하지 않도록 분포를 확인하고 비중을 조정한다. 구체적인 비율은 데이터 현황과 표본 검토 후 결정한다.

검토 기록은 기존 `reviews.json`의 ID·해시·결정·시각 형식을 확장해 승인·보류·제외를 기록한다. 원문, 입력 구성, 턴 묶음 또는 선별 규칙이 바뀌면 해시가 달라져 다시 검토 대상으로 돌아간다. `history.py show`와 `review`는 실제 모델 입력, 정답, 연결 근거와 미확인 항목을 함께 보여 준다. 미확인 사유를 명시적으로 확인하지 않으면 승인할 수 없다.

집계 보고서·표본 manifest·테스트 로그에는 대화 본문을 남기지 않는다. 본문은 명시적으로 실행한 로컬 `show`·`review` 화면에서 확인한다. 합성 학습 성공, 실제 후보 추출, 사람이 내린 품질 판정을 각각 별도 증거로 기록한다.

## 8. 학습·평가 데이터 분리

평가 목적을 두 가지로 나눈다.

| 평가 목적 | 분리 방식 |
|---|---|
| 평소 대화 상대에게 앞으로 더 잘 답하는가 | 이전 대화로 학습하고, 이후의 독립된 대화 구간으로 평가 |
| 다른 대화 상대에게도 효과가 있는가 | 일부 채팅방 전체를 평가용으로 보관 |

같은 메시지를 공유하는 사례와 이어진 대화 구간은 한쪽에만 배치한다. 같은 방에서 시간으로 나누더라도 맥락이 겹치는 사례가 분할 경계를 넘지 않도록 조정한다. 평가용으로 고정한 데이터는 이후 반복 학습에서도 제외한다.

동결 대상은 후보 ID뿐 아니라 **플랫폼·계정·방·원본 메시지 ID, 관련 대화 구간, 중복 그룹**까지 포함한다. 같은 전송이 `hist:`와 `send:`로 다시 나타나거나, 평가용 메시지가 이후 학습 사례의 맥락에 들어오는 경우도 차단한다. 단순히 창이 겹친다는 이유로 방 전체가 하나의 그룹이 되지 않도록, 독립된 대화 구간을 먼저 식별하고 분할 경계의 겹치는 사례를 조정한다. 분리 가능한 구간이 부족하면 그 사실과 남은 사례 수를 보고한다.

이 분리는 서로 연관된 사례가 학습과 평가 양쪽에 섞이는 문제를 줄이기 위한 것이다. 시간과 그룹을 고려한 평가 분리 원칙은 [scikit-learn 교차검증 문서](https://scikit-learn.org/stable/modules/cross_validation.html)를 참고한다.

중복은 입력과 답장의 조합 및 원본 대화 관계로 판단한다. 서로 다른 상황에서 나온 “감사합니다”가 같다는 이유만으로 모두 버리지는 않는다.

규칙·학습 설정을 조정할 검증 데이터와 최종 비교에 사용할 평가 데이터도 구분한다. 분할 비율과 최소 사례 수는 수집 현황을 확인한 뒤 정한다.

구현에서는 명시적인 `assignments`와 원본 출처 기반 배타 검사를 사용한다. 설계 당시 `prepare_examples`의 방 전체 `chat:` 키와 정답 문자열 `target:` 키에 의한 일괄 탈락을 원본 출처 기반 정책으로 교체한다. 세션 데이터와 과거 데이터에 동일한 분할 정책을 적용한다.

## 9. 어댑터 비교 평가

동일한 평가 대화에 대해 다음 세 가지의 실제 출력을 비교한다.

| 비교 대상 | 목적 |
|---|---|
| A. 기본 모델 | 기준선 |
| B. 기본 모델 + 새 어댑터 | 개인화 학습 효과 확인 |
| C. 기본 모델 + 과거 답장 예시 제공 | 학습 없이 예시를 제공하는 방식 대비 실익 확인 |

C의 예시는 학습 분할에서만 선택하고 평가 시점 이전의 사례만 사용한다. 평가 정답이나 같은 평가 대화의 파생 사례를 예시로 제공하지 않는다. 예시 선택 규칙을 고정하고 총 입력 예산·공통 맥락·생성 설정을 통제하며, 토큰 수와 지연도 함께 보고한다. 이미 활성 어댑터가 있다면 현재 운영 모델도 기준선에 포함한다.

과거 예시는 각 예시의 메타데이터와 대화를 담은 별도 참고 영역으로 전달한다. 현재 대화의 `user/assistant` 턴 앞에 끼워 넣지 않는다. 현재 `turn_metadata`의 순서와 발화자·답장 관계가 어긋나는 것을 막기 위해서다. 예시의 사실과 결정은 현재 대화의 사실로 취급하지 않도록 표시하며 이 참고 영역까지 포함해 토큰 예산을 검사한다.

| 평가 항목 | 확인할 내용 |
|---|---|
| 역할 정확성 | 누가 만들고, 요청하고, 수행했는지 유지하는가 |
| 사실 정확성 | 근거 없는 완료·일정·승인을 만들어내는가 |
| 답장 적합성 | 상대의 말에 자연스럽게 이어지는가 |
| 개인화 | 내 말투와 길이에 가까우며 수정할 부분이 줄었는가 |
| 답변·보류 적절성 | 답할 수 있는 상황에서 불필요하게 보류하거나, 보류가 필요한 상황에서 확정 답장을 만드는가 |

과거 답장과의 글자 일치는 주된 기준으로 삼지 않는다. 같은 상황에 적절한 답장은 여러 개일 수 있다. 학습 손실이 줄었다는 사실만으로 역할 반전이 해결됐다고 판단하지 않는다.

역할이 뒤바뀌는지 확인할 전용 평가 사례를 별도로 유지한다. 실제 대화에서 추출한 학습 사례와 별도 구성한 평가 사례는 출처를 구분한다. 표본 규모와 오류 수를 함께 보고하고, 작은 표본의 성공을 일반적인 정확도 개선으로 단정하지 않는다.

‘답장한 사례’만으로 학습할 때 보류가 줄어드는지 별도로 확인한다. 정답 기준은 사용자 또는 위임받은 검토자가 정한 답변 가능·보류 필요 조건이며, 기본 모델의 보류를 그대로 정답으로 삼지 않는다. 일정이나 링크가 등장했다는 이유만으로 항상 `<ABSTAIN>`해야 하는 것도 아니다. 근거 없는 확정과 적절한 확인 의향·질문을 구분해 판정한다.

개인화 평가는 A/B/C의 출처를 가리고 선호와 수정 필요성을 비교한다. 역할 반전·근거 없는 확정·불필요한 보류가 악화되지 않는지 함께 본다. 검증 데이터로 학습 설정과 체크포인트를 선택하고, 최종 평가 데이터로 반복 튜닝하지 않는다. 평가 손실은 보조 지표이며 적용 기준의 표본 수와 허용 오류 수준은 아직 미정이다.

학습된 어댑터는 비교 결과를 검토한 뒤 적용 여부를 결정한다. 적용하면 이후 추천 모델의 개인화 가중치가 바뀐다.

## 10. 설계 시작 시점의 구현과 데이터 근거

아래는 2026-10-01 확인한 코드 기준의 출발점이다. 이후 구현 진행 상태는 13장에서 관리하며, 이 절의 미구현 설명을 최신 코드 상태로 해석하지 않는다.

| 구성 | 현재 범위와 이 설계의 관계 |
|---|---|
| [추천 입력 구성](../packages/reply-model/worker.py) | 구조적 사전 검사와 단일 생성 호출을 사용한다. `build_generation_input`을 학습과 추천의 입력 일치에 활용할 수 있다. |
| [지속 학습 도구](../packages/reply-model/continual.py) | Inboxd 응답 세션에서 직접 입력하고 전송한 답장의 후보 수집·검토·학습·평가를 연결한다. 과거 메신저 전체를 답장 사례로 변환하는 기능은 아직 없다. |
| [개인화 학습 도구](../packages/reply-model/personalization.py) | 검토된 사례의 LoRA 학습·평가·적용·롤백 도구가 있다. 이 문서의 새 분할 정책과 후보 변환은 별도 구현이 필요하다. |
| [메시지 저장 구조](../crates/inboxd-core/src/store.rs) | 발신자, 답장 참조, 수정·삭제 정보, 수집 범위를 저장할 구조가 있다. 각 플랫폼의 실제 데이터 충족 여부는 확인해야 한다. |

현재 개인화 도구의 분할 방식은 시간순으로 나눈 후 채팅방과 반복 정답 등이 경계를 넘으면 제외하는 방식이다. 이 문서에서 제안한 두 종류의 평가와 입력·정답 조합 중심 중복 처리는 아직 구현된 동작이 아니다.

추출 구현에서 고려할 코드상의 한계는 다음과 같다.

- [실시간 관측 저장](../crates/inboxd-storage/src/observations.rs)은 본문·발신자·시각을 갱신하지만 답장 참조·첨부·수정 시각을 새로 공급하지 않는다. 기존에 수집된 참조 필드는 보존한다. 따라서 참조가 없다고 일괄 가정하지 않고 실제 보유 여부를 집계한다.
- 메시지의 수정 전 본문 이력을 보관하는 구조는 없다. `edited_at` 부재와 수정되지 않았다는 사실을 구분해야 한다.
- 현재 카카오톡·텔레그램·Slack worker는 첨부 목록을 빈 배열로 내보낸다. 카카오톡 bounded history에는 커서 제약도 있다. 수집 API 호출만으로 참조·첨부·과거 원문을 모두 복원할 수 있다고 가정하지 않는다.
- `message.inbox`·`message.recent`는 답장 참조와 발신자 역할을 반환하지 않는다. CLI의 `chat list`·`message inbox`는 페이지 인자를 전달하지 않으므로, 과거 후보 추출은 전용 경로를 둔다.
- `continual.py`는 현재 `incoming_message_ids` 없이 입력을 재구성한다. 세션 export에 당시 source 정보를 추가하고 5장의 읽음 상태 정책을 함께 적용해야 한다.

현재 학습 도구의 2,048토큰 제한과 추천의 맥락 길이 제한도 서로 다르다. 구현 시 실제 모델 입력과 정답을 함께 계수하고 필수 맥락을 유지할 수 있는지 확인해야 한다.

운영 명령과 기존 도구의 저장·보관 한계는 [개인화 도구 문서](../packages/reply-model/PERSONALIZATION.md)에 기록되어 있다. 이 설계 문서 저장은 원본 대화의 추가 수집·내보내기나 학습 실행을 포함하지 않는다.

### 기존 문서에 보고된 규모

다음은 통합 전 설계 문서가 2026-10-01의 읽기 API 집계로 보고한 값이다. 이번 통합에서 다시 집계하거나 당시 조회 범위의 완전성을 재검증하지 않았다. 최신 운영 현황이나 확정된 학습 가능량으로 사용하지 않는다.

| 플랫폼 | 방 | 메시지 | 내 발신 | 선별 전 답장 턴 | 내 발신이 있는 방 |
|---|---:|---:|---:|---:|---:|
| 카카오톡 | 60 | 730 | 260 | 116 | 30 |
| Slack | 25 | 365 | 73 | 38 | 13 |
| 텔레그램 | 15 | 374 | 89 | 57 | 11 |
| 합계 | 100 | 1,469 | 422 | 211 | 54 |

답장 턴은 관측된 메시지에서 상대 발언 뒤의 연속된 내 발신을 묶어 센 값이다. 211건은 이 추출 규칙에 따른 선별 전 후보 규모이며 전체 기록의 상한이나 승인 사례 수가 아니다. 같은 집계에서 수집 범위 근거가 있는 방은 1개, 발신자 3명 이상인 방에서 나온 턴은 98개로 보고됐다. 실제 추출에서는 수집 범위와 답장 연결을 다시 확인한다.

또한 합성 45자 본문으로 운영 입력을 구성한 기존 측정은 맥락 10개에서 1,729토큰, 20개에서 2,909토큰, 40개에서 5,269토큰이었다. 이는 토큰 예산 문제를 확인할 근거이며 실제 대화 길이 분포를 대신하지 않는다. 모든 운영 입력이 2,048토큰을 초과한다고 해석하지 않는다.

## 11. owner 전용 추출 계약

`trajectory.list`의 `history_candidates`와 `history_inventory` 분기로 후보와 수집 현황을 나눈다. 기존 `training_candidates`와 같이 owner 인증 로컬 UDS를 통해 제공하며 MCP 역할에 노출하지 않는다. 작업 트리에 구현된 인터페이스는 다음과 같으며 설치본 연결 검증은 별도 완료 기준이다.

| 요청 | 응답 |
|---|---|
| `{history_candidates:true, limit?, cursor?, platform?, account?, chat_id?}` | `candidates`, `omitted`, `next_cursor`. 후보 페이지 크기는 1~25개 |
| `{history_inventory:true, limit?, cursor?, platform?, account?}` | 본문 없는 `rooms`, `version`, `next_cursor`. 현황 페이지 크기는 1~500개 |

현황에는 메시지·내 발신·관측 발신자·답장 참조 건수, 최초·최근 시각, 내 계정 식별 상태, 수집 구간·제한·삭제 건수를 포함한다. 수집 구간과 제한 목록은 각각 최대 4개만 포함하므로 전체 건수와 구분한다.

- `(platform, account, chat_id, ts, msg_id)` 기준의 안정적인 순서와 불투명 커서를 사용한다. 조회 범위·규칙 버전을 고정하고 재시도 시 원본 ID로 중복을 제거한다.
- 삭제되지 않은 내 발신과 그 이전 상대 발언을 연결해 넓은 후보를 만든다. 실제 답장 대상과 턴 경계는 4~6장의 기준으로 확인한다.
- 맥락은 5장의 읽기 전용 공통 함수로 구성한다. 입력 본문뿐 아니라 역할·참조·조회 시점도 운영 경로와 같은 기준을 쓴다.
- 페이지는 기존 방식의 48,000바이트를 초기 예산으로 삼되, 응답 메타데이터까지 포함한 전체 JSON의 바이트 수를 검사한다. 단일 후보 초과는 `candidate_too_large`로 기록하고 커서를 전진시킨다. 정답을 몰래 잘라 맞추지 않는다.
- 과거 원문을 매번 다시 조회하므로 추가 수집·수정·삭제에 따른 변화를 반영한다. 같은 후보 ID라도 내용이 달라지면 이전 검토 승인을 승계하지 않는다.

후보 레코드의 주요 필드는 다음과 같다. 공통 메시지 키는 `[platform, account, chat_id, msg_id]` 배열을 공백 없는 JSON 문자열로 직렬화한다. 저장소는 내 발신 메시지별 후보를 내보내고, `history.py`가 4장의 규칙에 따라 답장 턴을 구성한다.

| 필드 | 계약 |
|---|---|
| `id`, `source` | 과거 후보 `hist:`와 세션 후보 `send:`를 구분하는 ID, `history / session` |
| `chat` | 플랫폼·계정·방의 복합 식별자 |
| `context` | 원본 메시지 ID·발신자 ID·역할·시각·본문·답장 참조 |
| `targets` | 정답으로 묶일 원본 메시지 ID·시각·본문·답장 참조·작성 출처 |
| `source_message_keys` | 분할·중복·삭제 추적용 복합 메시지 키. 입력과 정답 모두 포함 |
| `reply_linkage` | 답장 연결 근거, 실제 답장 대상, 모델 입력의 대상과 일치 여부 |
| `unseen_state`, `incoming_message_ids` | 당시 근거가 있는 경우 `known`과 ID 목록. 미확인은 `unknown`과 `null` |
| `context_edit_state` | `verified_unchanged / edited_after_target / unknown`과 근거 |
| `coverage` | 후보의 맥락 구간을 덮는 수집 근거와 누락·제한 구간 |
| `authorship` | `manual / edited_suggestion / unchanged_suggestion / unknown`과 전송 기록 연결 |
| `versions`, `review_hash` | 입력·턴·선별 규칙 버전과 원본 내용에 결합된 검토 해시 |

`unknown` 값은 수집 단계에서 보존하고 5장의 정책에 따라 모델 입력에서도 미확인 상태로 표현한다. 원본 내 답장의 참조는 `reply_linkage` 검토에만 사용하고 모델 입력의 미래 정보로 추가하지 않는다.

## 12. 학습·적용과 보관

기존 MLX LoRA 도구를 사용하고, 매 주기 기본 모델에서 현재 승인된 학습 데이터로 다시 학습한다. 두 데이터 출처를 합친 뒤 선별·중복 제거·분할을 공통으로 적용한다.

| 항목 | 통합 제안 |
|---|---|
| 입력 길이 | 실제 입력+정답 분포와 로컬 메모리·시간을 측정해 `max_seq_length`를 설정화. 긴 사례는 선별 단계에서 보류하고 학습기에도 최종 검사 유지 |
| 맥락 축소 | 필요하면 운영·학습의 선택 규칙을 함께 변경. 메타데이터 축소도 입력 버전 변경과 품질 재평가를 거침 |
| 학습 횟수 | 초기 파일럿의 기본값 100회에 고정하지 않고 사례 수·배치 크기·목표 에폭을 바탕으로 계산하고 검증 결과로 조정 |
| 학습 대상 | `mask_prompt` 유지. 마지막 사용자 답장에만 손실이 계산되는지 실제 토크나이저·학습 경로에서 확인 |
| 체크포인트 | 검증 주기마다 저장하고 검증 결과로 선택. 최종 평가셋을 선택에 사용하지 않음 |
| 자원 사용 | 긴 합성 맥락으로 메모리·시간을 먼저 측정하고, 추천 워커와 동시에 실행할 때 지연도 확인 |
| 적용 | 비교 평가 후 `activate --reviewed`로 적용하고 `rollback` 경로 유지. 학습 완료만으로 활성 어댑터를 바꾸지 않음 |

기존 지속 학습의 학습 100 / 검증 20 / 평가 20 및 새 학습 25건 조건은 파일럿 설정이다. 과거 데이터에 충분한 기준인지 아직 확인하지 않았다. 학습 경로가 실행되는지 확인하는 실험과 품질 개선을 판단하는 실험의 데이터 요구량을 구분한다. 기존 04:00 스케줄의 `cycle`에 과거 후보와 응답 세션을 함께 연결했다. 승인 수와 평가 분할 조건을 충족하지 않으면 학습하지 않는다.

원문은 SQLCipher에 보관하고 추출·검토 과정은 로컬 메모리에서 처리한다. 검토·분할·상태 파일에는 ID·해시·결정·건수를 남긴다. 학습 JSONL은 제한된 권한의 임시 디렉터리에 만들고 종료 시 제거하며, 비정상 종료 후 잔여 파일 정리도 다룬다.

현재 어댑터·로그 파일은 owner 전용 권한이며 애플리케이션 암호화가 아니다. 원문 삭제는 다음 주기의 후보를 무효화하지만 이미 학습된 가중치에서 영향을 제거하지 않는다. 해당 원문을 제외한 재학습·새 어댑터 적용 또는 그 원문을 학습하지 않은 버전으로의 롤백이 필요하다. 상대 발언도 입력으로 사용되므로 손실 마스킹만으로 정보가 가중치에 남지 않는다고 보장하지 않는다.

- **축소 실행의 종료와 체크포인트 검증**: 22회 optimizer step 및 마지막 validation까지 완료해 검증 loss가 3.170→3.076으로 줄고 MLX peak 22.959GB를 기록했다. 그러나 체크포인트 저장 직후 `training_rss_limit`로 종료돼 원래 실행은 실패 상태를 유지한다. 최종·22회차 파일의 동일 해시, 62개 tensor/2,704,896개 parameter, 유효한 파일 범위와 finite 값을 확인한 뒤 별도 사본을 만들었다. 사본의 `mode=checkpoint-recovery`는 오프라인 평가 전용이며 `activate --reviewed`와 운영 worker의 `mode=train` 검사에서 거부된다. 사본의 복구 검증 완료를 원래 학습 프로세스 정상 종료로 해석하지 않는다. 별도 검증·독립 평가·눈가림 비교를 이어서 수행한다.
- **예시 비교의 입력 정렬**: C 방식의 과거 예시를 현재 발언 앞에 그대로 붙이면 현재 `turn_metadata`와 순서가 어긋났다. `isolated-reference-v1`은 각 예시의 자체 메타데이터와 발언을 별도 참고 영역에 넣고 현재 발언·메타데이터는 그대로 유지한다. 예시는 학습 분할의 과거 사례만 사용하고 전체 입력 예산을 넘으면 줄인다. 현재 대화 불변·예시 메타데이터 보존 회귀를 추가했다.

- **운영 자원 설정**: 여유 메모리를 고려해 스케줄 기본 길이는 2,048, batch 1, epoch 2를 유지한다. 4,096은 명시적으로 선택할 수 있다. 학습·손실 평가 자식마다 기본 2시간·RSS 20GiB·macOS 전체 swap 증가 4GiB를 감시한다. - 이번 명시적 실험은 RSS 28GiB·전체 swap 증가 4GiB·최대 2시간의 감시를 사용한다. 48GiB Mac의 현재 가용 상태와 이전 저장 직후 RSS 초과에 맞춘 한 번의 설정이며 일일 스케줄의 기본 RSS 20GiB를 바꾸지 않는다. 학습뿐 아니라 비교 생성도 감시 대상에 포함하고 자원 경과를 본문 없는 owner 전용 보고서에 남긴다.
- 정상 종료한 학습 산출물만 검증 손실로 선택한다. 이후 기존 모델과 동일 입력으로 비교하고, 모델명을 가린 의미 판정을 저장한 뒤 매핑을 공개한다.

### 첫 재실행의 자원 중단과 다음 실험

`safety-pilot-v2`는 첫 검증 20배치(loss 2.776, 94.6초) 후 학습 초반에 `training_swap_limit`로 종료됐다. 전체 187.4초 동안 외곽 최대 RSS는 7.32GiB, 시스템 swap 증가 최대는 4.78GiB였고 학습 자식에서 관측한 최대 증가는 4.84GiB였다. RSS는 Metal 메모리 전체를 직접 나타내지 않으므로 낮은 RSS만으로 여유가 충분했다고 판단하지 않는다. 체크포인트 0개, 남은 실행 자식 0개이며 선택·회귀·fresh 평가는 실행되지 않았다. 당시 임시 파일 검사는 일부 경로만 확인했으므로 실제 OS 임시 디렉터리의 잔여는 최종 감사에서 재확인한다. 실패 상태와 계획을 보존한다.

당시 Inboxd 운영 추천 worker 두 개가 합계 약 10.25GiB RSS를 차지했다. 다음 `safety-pilot-v3`는 학습 데이터·길이·학습량·RSS/swap 한도를 유지하고 이 동시 점유만 제거하는 실험이다. 원문·승인 해시 재조회 후 owner lock과 실행 파일을 검증한 Inboxd 데몬에 정상 종료 신호를 보내고, 학습·평가가 끝나거나 실패하면 외곽 정리 단계에서 `inboxd daemon start`로 복구한다. 다른 앱의 프로세스는 종료하지 않는다. 서비스 중단은 이 명시적 로컬 실험에 한하며 자동 스케줄의 동작으로 추가하지 않는다.

`v3` 실행 계획은 `c7c94ee5081a34f22150e6777c2be9857fd2fbfe22733ca0451d1fd09b1d66da`로 고정했다. 실제 분할·검토 출처·합성 보강·fresh 동결 해시는 v2와 같고, 데몬 일시 종료 옵션과 실행기 코드만 바뀌었다. 내부 학습 실패 및 외곽 자원 실패 시 CLI 복구 경로를 fake CLI로 검사한 테스트 2개가 통과했다. 실험 산출물은 기존 검증 디렉터리의 `verification-20261002/safety-pilot-v2/`, `safety-pilot-v3/`에 날짜·판정별로 분리한다.

`v3`는 운영 데몬 종료로 free 메모리가 16.09→23.26GiB, 압축 메모리가 4.44→2.53GiB로 개선된 상태에서 시작했다. 첫 검증 loss 2.776/87.7초, 10회 학습 loss 2.492, 20회 loss 2.439까지 진행했지만 이후 `training_swap_limit`로 종료됐다. 학습 자식은 최대 RSS 20.37GiB, 시작 swap 2.909GiB 대비 최대 증가 4.201GiB, 마지막 보고 MLX peak 29.770GB였다. 전체 416.0초, 학습 자식 362.1초였으며 체크포인트 0개·평가 미실행이다. 데몬은 finally 경로로 복구되어 ready·암호화 저장소 ready를 확인했고, 남은 학습 자식은 0개다. 임시 staging은 당시 확인 경로 외에 실제 OS 임시 디렉터리를 최종 감사에서 다시 확인한다. 운영 추천 worker만이 자원 실패 원인이라고 단정하지 않는다.

다음 `safety-pilot-v4`는 실제 학습의 전체 길이 2,048토큰 초과 6건만 제외한다. 본문을 자르거나 기존 동결 분할을 바꾸지 않고, 실험의 제외 ID·해시·길이 사유를 기록한다. 예상 실제 사용량은 학습 22/검증 12/평가 22, 합성 보강 후 54/20/22다. 검증·평가 입력 예산 4K, 2에폭, 자원 한도, 데몬 일시 종료는 유지하며 데이터 수에 따라 108회 업데이트·54회마다 저장한다. 제외한 6건은 C 예시 검색에도 넣지 않는다. 이전 축소 실험에서 실제 2K 이내 학습은 마지막 저장까지 도달했으므로, 이번에는 같은 길이 제약과 보강 사례로 정상 종료 가능성을 확인한다. 새 평가 24건은 아직 생성되지 않았다.

중첩 종료 회귀는 리더가 살아 있는 timeout/RSS/cancel 경로를 검증한다. 리더가 먼저 강제 종료되어 자식이 재부모화된 경우까지 영구 추적하는 구현은 아니며, 모든 외부 종료 상황의 무잔여를 보장하지 않는다. 위 실패 실행의 프로세스 잔여 0개는 각각 실제 종료 후 확인한 결과다. 임시 디렉터리는 실제 OS 경로까지 최종 감사에서 재확인한다.

학습 진행 중 보강 자료를 재점검하여 합성 학습 32건 중 `unknown_information-03` 정답이 모델의 첨부 본문 부재를 사용자의 열람 가능성·상태로 표현하는 문제가 있음을 확인했다. 모델에 내용이 없다는 사실은 사용자가 못 봤다는 근거가 아니다. 현재 실행의 자료·해시는 수정하지 않고 이 한계를 기록한다. 향후 자료는 사용자 상태를 단정하지 않는 정보 요청으로 교정하되, 현재 실행이 교정된 자료로 학습됐다고 표시하지 않는다. 출력 검토에서도 과거 열람 상태 주장과 미래의 확인 의사를 구분한다.

`v4` 학습은 108회 업데이트·정답/종료 1,750토큰·1,045.0초에 정상 종료됐다. 학습 manifest는 `mode=train`, `status=complete`이고 54/108회차 두 체크포인트가 저장됐다. 학습 가드의 RSS 최대는 26.917GiB(한도 28GiB), swap 추가 증가 최대는 0이었다. MLX peak는 22.968GB로, RSS와 다른 지표다. 학습 도중 validation loss는 초기 2.776→54회차 2.621→108회차 2.708로 후반에 악화됐으므로 마지막 시점을 자동으로 선택하지 않는다. 별도 validation 재평가로 두 체크포인트를 비교하며, 이 시점에는 추천 품질 판정과 운영 적용이 아직 끝나지 않았다.

`v4`의 validation 전용 재평가에서 고유 체크포인트 2개 중 **54회차(loss 2.610)**를 선택했다. 최종 파일과 108회차 파일의 같은 SHA는 중복 평가하지 않았다. 선택 결과는 manifest에 남기고 `selection_required=false`로 기록했으며, 이후 실제 test 22건의 base/adapter 손실 및 익명 답장 비교를 별도로 수행한다.

선택된 54회차 가중치의 무결성: 62개 float32 tensor/2,704,896개 parameter가 모두 finite이고 체크포인트 SHA는 `9444d6341c01c85017fa882d5baacbc204b788f348e0051fa5fc87b86cea19eb`다. 설정의 원본 모델 경로와 manifest의 base ID가 실행 계획과 일치한다. 실제 대화 22건의 관측 회귀 평가 loss는 기본 모델 3.528→선택 모델 3.016(-14.5%)이었다. 이 수치는 정답 답장의 예측 손실이며 생성 답장의 역할·사실·거절 보존 판정과 구분한다.

`v4`의 전체 학습·선택·손실 평가·기존 비교·fresh24 생성이 외곽 실행 exit 0으로 끝났다. 외곽 RSS 최대는 26.824GiB, 추가 swap 증가 최대는 0이었다. 학습 자식과 외곽 샘플링 시각 차이로 peak 값은 조금 다르다. 운영 입력의 기존 4상황/8출력도 별도 가드에서 exit 0으로 생성했다(RSS 최대 5.298GiB, swap 증가 0). 데몬과 암호화 저장소 ready를 확인했고, 실제 `tempfile.gettempdir()`에서 두 private staging prefix 잔여 0개, 실행 디렉터리 권한 이상 0개를 확인했다.

향후 보강 자료의 `revision=2`에서는 앞서 발견한 첨부 열람 상태 단정을 중립적인 세부 내용 요청으로 교정했다. `curriculum_revision`과 fixture hash로 버전을 구분한다. 이번 v4 가중치는 **교정 전 revision 1** 자료로 학습됐으며, 그 정확한 모듈·train/valid fixture와 SHA는 v4의 `provenance/`에 별도로 보존했다. 향후 교정을 이번 학습에 소급해 반영했다고 표시하지 않는다. 교정 후 기존 전체 Python 테스트 176개, 별도 fresh CPU 테스트 4개와 typecheck·boundary 검사가 통과했다.

## 16. 카카오톡 우선 전체 접근 가능 기록 확보와 후속 개선

### 서버 수집과 카카오톡 로컬 원천 실측

연결 목록 86방의 서버 수집은 115페이지를 저장하고 신규 메시지 457건을 추가했다. 서버가 제공하는 끝에 도달한 방은 63개(카카오톡 19·텔레그램 10·Slack 34)다. 카카오톡 나머지 23방은 방의 마지막 메시지 ID가 존재하지만 서버 기록 응답이 비어 있고 다음 커서도 없어 `server_history_gap_without_continuation`으로 구분한다. 이 상태를 빈 방이나 전체 수집 완료로 표시하지 않는다. 서버 수집 직후 정규 저장소는 2,171건, 내 발신 566건이었다.

Mac 카카오톡 26.7.0의 실제 로컬 SQLCipher DB를 읽기 전용으로 검증했다. 앱의 암호화 DB와 WAL을 함께 안정된 임시 스냅샷으로 복사하고, 계정·기기 식별 일치 및 무결성을 확인했다. 확인된 원천은 **269방·43,001건·내 발신 17,608건**이며 기간은 한국 시각 2024-12-31부터 2026-10-03까지다. 정확한 일반 텍스트 유형은 34,814건이며, 내 발신 중 일반 텍스트 15,180건·인용 답장 297건이 있다. 이는 원천 수이며 학습 승인 수가 아니다.

로컬 가져오기는 owner 인증과 현재 연결된 내 계정 일치를 요구한다. 전체 원천 행을 암호화 장부에 보존하고 페이지 해시·원자적 커밋·재실행 중복 방지를 적용한다. 메시지 본문을 명령 인자로 전달하지 않는다. 원격 조회·읽음 커서 변경·추천 작업 생성은 이 경로에 포함하지 않는다. 서버 수집의 체크포인트와 로컬 원천의 장부는 별도로 유지한다.

일반 텍스트·인용 답장 코드 1/26만 텍스트 정답 후보로 취급한다. 사진·파일 등은 공유 맥락에 자리표시자로 남기고, 삭제 플래그가 붙은 코드를 텍스트 코드로 되돌려 해석하지 않는다. `history-v3`는 비텍스트 정답을 제외하고, 알 수 없는 원천 유형·복원할 수 없는 삭제 맥락·수정 이력이 있는 원문의 당시 버전 부재를 각각 `archive_type_unverified`, `archive_deleted_context_unrecoverable`, `archive_revision_unrecoverable`로 보류한다. 원천 revision을 임의의 수정 시각으로 변환하지 않는다. 단순히 사진이 있다는 경고와 실제로 그 내용이 필요한지는 이후 의미 검토에서 구분한다.

| 합계 | **44,382** | **17,879** |

서버에서 제한된 카카오톡 23방 중 21방은 로컬 기록을 추가로 확보했다. 나머지 2방은 로컬에도 기존 메시지 1건씩만 있고 내 발신은 없었다. 따라서 더 오래된 기록을 확보했다고 표시하지 않는다. 카카오톡 원천 집계와 서버 집계는 중복이 있어 단순 합산하지 않는다.

가져오기 전후 전체 메시지 해시 175건의 차이를 발견해 이전 암호화 백업과 대조했다. 기존 카카오톡 824건 전체에서 본문·작성자·시각·수정/삭제 필드 변화와 누락은 0건이었다. 차이는 일반 동기화의 `observed:<order>` revision 증가뿐이었으며 가져오기 경로는 기존 정규 메시지를 덮어쓰지 않았다. 해시 차이를 무시하고 동일하다고 처리하지 않고 이 근거를 별도 기록했다.

설치 후 실제 데몬 재시작에서 기존 스키마 6의 엄격한 객체 검사와 임시 수집 테이블이 충돌하는 문제를 발견했다. 암호화 저장소를 중지 상태에서 백업하고, 수집 체크포인트와 로컬 원천 장부 3개 테이블을 정식 스키마 7로 편입했다. 정확히 일치하는 과도기 테이블만 보존해 이전하고, 변형된 정의나 임의의 추가 객체는 계속 거절한다. 실제 StorageActor의 이전·가져오기·종료·재열기와 변형된 스키마의 원자적 실패를 포함한 저장소 테스트 90개가 통과했다(별도 10만 건 성능 테스트 1개는 선택 실행). 운영 데몬은 스키마 7·암호화 저장소 ready로 복구됐고, 서버 수집 86방의 체크포인트가 설치 전과 모두 일치함을 읽기 전용으로 확인했다. 되돌리기 자료는 기존 실행 파일과 이전 전 암호화 DB를 별도로 보존한다.

가져온 원천의 품질 분류도 점검했다. 공개 [node-kakao의 원천 유형 정의](https://github.com/storycraft/node-kakao/blob/stable/src/chat/chat-type.ts)로 확인되는 이모티콘·투표·통화 등 13종, 1,929건은 알려진 비텍스트 유형으로 구분한다. 내용을 알 수 있다는 뜻은 아니므로 자리표시자는 유지하고 `external_content_likely` 경고 아래 개별 의미 검토를 요구한다. 유형 0/100/1999의 메시지 1,005건은 미확인으로 남긴다. 삭제 플래그 398건과 복원할 수 없는 수정 이력도 계속 보류 근거다. 이 분류 보완으로 학습 승인 수가 정해지는 것은 아니다.

원천의 인용 답장과 정규 저장소의 연결도 대조해, 원천에는 명시적인 답장 대상이 있지만 기존 정규 기록에는 없는 유형 26 메시지 24건을 확인했다. 임의로 직전 상대 발언에 대한 답장으로 해석하지 않도록 `archive_linkage_unrecoverable`을 적용한다. 관측 발신자가 두 명인 경우에도 방 종류가 확인되지 않으면 `room_kind_unverified` 경고와 개별 수신자 검토를 요구한다. 후속 변환 규칙 `history-v4`는 이런 출처·연결·방 종류를 검토 해시에 반영한다. 후보·토큰 길이 집계와 새 의미 검토·학습은 이 보완 후 진행한다.

분류·인용 연결 보완 설치 후 실제 데몬을 다시 시작하고 암호화 장부 43,001건/269방/1,182페이지와 정규 저장소 44,382건/내 발신 17,879건이 유지되는 것을 독립적으로 재확인했다. 운영 생성 입력은 `reply-v4`이며 활성 어댑터는 바꾸지 않았다. 이후 전체 플랫폼의 과거 답장 후보와 2K/4K 토큰 길이 집계를 시작했다.

첫 대규모 추출에서 페이지마다 약 169ms가 걸려 원인을 측정했다. 과거 대화 조회에도 추천 이력 보존기간 정리 6개 쿼리가 반복 실행되고 있었고, 만료 대상이 0개여도 약 159ms를 사용했다. 과거 후보·방 현황 조회를 보존기간 정리보다 먼저 분기하고, 과거 시각 조건이 있는 맥락 조회는 인덱스 범위 검색을 쓰도록 수정했다. 일반 추천 이력의 보존기간 정리는 유지한다. 원래 추출 프로세스는 5,412개 후보까지 읽은 시점에서 종료하고 본문 없는 중단 기록만 남겼으며, 부분 데이터는 동결하거나 학습에 사용하지 않았다.

수정 검증 58개가 통과했고, 설치 전후 실제 조회 12개의 전체 결과 해시·건수·바이트가 모두 일치했다. 대표 카카오톡 첫 페이지 7건의 조회는 4.24ms로 약 40배 빨라졌다. 이는 대표 조회의 실측이며 전체 토큰화·검수 시간의 40배 단축을 뜻하지 않는다. 수정 후 전체 스냅샷 추출을 다시 시작했다.

### 전체 변환 후보와 길이 제약 확인

재추출·토큰화·동일 원천 재조회가 368.6초에 완료됐다. 첫 조회의 원천 후보 17,445건과 전송 크기 제한으로 생략된 후보 285건은 두 번째 조회에서도 모두 일치했다. 생략은 48KB 응답 한도에 관한 것으로, 암호화 저장소의 원본이 삭제되었다는 뜻이 아니다. 턴을 묶은 결과는 194방의 10,426개 대화·답장 후보이며, 원천 manifest SHA256은 `ada5d5e633bfde02ac1f3357118c603b0d9db6b652c2ee8222d5b08689b96d90`이다.

| 전체 길이 조건 | 카카오톡 검토 가능 | 텔레그램 검토 가능 | Slack 검토 가능 | 합계 |
|---|---:|---:|---:|---:|
| 2,048토큰 | 391 | 29 | 21 | **441** |
| 4,096토큰 | 3,783 | 89 | 38 | **3,910** |

위 수치는 내용 검수를 시작할 수 있는 수이며 승인·학습 수가 아니다. 4K 후보 중 운영 생성의 입력 3,904 + 출력 192토큰 예산까지 충족하는 것은 3,896건이다. 카카오톡 후보의 전체 길이 중앙값은 2,500토큰이며, 2K 한도 초과는 9,215건이다. 원천 유형 미확인 3,488건, 삭제 맥락 복원 불가 1,832건, 수정 이력 복원 불가 1,183건 등도 보류에 영향을 준다. 사유는 한 후보에 여러 개가 붙으므로 합산하지 않는다.

기존 검증·평가 원본 예약을 보존하고, 이전 판정을 받은 242건은 보류·제외 여부와 관계없이 관측된 사례로 구분한다. 새 실제 최종 평가는 이들의 방과 기존 예약 원천을 제외한 곳에서 선정한다. 우선 운영 입력 `reply-v4`, 전체 사례 길이 2K 이하 학습, 4K 검증·평가 조건을 유지해 확장 효과를 확인한다. 본문을 잘라 기준에 맞추지 않는다. 후보 검수, 재학습 및 품질 비교는 아직 완료되지 않았다.

새 실제 평가의 방 분할은 내용·출력 검토 전에 고정했다. 카카오톡 10방·Slack 3방에서 평가 48건을 목표로 우선 60개 후보를 검토하고, 필요한 경우에만 정해진 순서의 예비 36개를 사용한다. 검증은 별도 카카오톡 6방·Slack 2방에서 28건을 목표로 한다. 선택하지 않거나 보류한 후보가 있어도 예약한 방 전체를 학습에서 제외한다. 기존 관측 방 36개 및 이전 원천 예약과의 중복, 새 검증 방과 평가 방의 중복은 모두 0이었다. 새 방 예약 후 처음 확보한 방의 2K 학습 후보 상한은 295건이며, 아직 의미 검수 승인을 받은 수가 아니다. 텔레그램에는 검토 가능한 미관측 방이 없어 새 텔레그램 일반화 증거를 주장하지 않는다.

독립적으로 작성한 합성 개발 24건과 최종 48건은 학습 전에 구분해 봉인했다. 개발 24건에서 기본 모델만 먼저 생성해 50.42초에 완료했고 최대 RSS는 약 5.33GiB, swap 증가는 0이었다. 주관 에이전트의 개발 진단은 명확한 의미 실패 11건, 별도 역할 불확실 1건, 유용성 평균 3.00이었다. 기존 거절을 미확정 상태로 바꾸기, 타인에게 온 요청을 내 작업으로 받아들이기, 서로 다른 결정 범위를 합치기, 확인 질문이 가능한데 답장을 포기하기가 확인됐다. 이 판정은 모델명을 가리지 않은 개발 진단이며 최종 품질·적용 증거가 아니다. 최종 48건의 출력은 아직 생성하지 않았다.

개발 생성 자식은 정상 종료했지만 외곽 스크립트가 예전 평면 상태 키로 준비 여부를 검사해 exit 1을 기록했다. 원래 실패 기록을 보존하고 실제 중첩 `encryption.ready`·`schema_valid`·스키마 7을 독립 조회해 데몬 복구를 확인했다. 생성 보고서는 수정하거나 다시 생성하지 않았다. 후속 실행기는 실제 상태 구조를 사용한다.

새 방과 기존 평가 원천의 경계를 실제 문맥 전체에 적용한 뒤, 개별 학습 검수 대상으로 남은 것은 **350건(카카오톡 322·텔레그램 16·Slack 12)**이다. 이는 앞선 441건에서 평가·검증 예약과 출처 경계를 반영한 수이며 승인 수는 아니다. 검토자는 원래 문맥·묶인 정답·정확한 운영 입력을 읽고 승인·보류·제외 및 행동 유형을 남긴다. 일부 문맥에서 실제 비밀번호나 접속 암호가 발견돼, 해당 원천 메시지가 포함된 후보를 학습·검증·평가에서 제외하는 별도 격리 목록을 추가한다. 원본은 수정하지 않고 비밀값은 보고서에 남기지 않는다. 숨긴 문맥을 원래 입력으로 승인하지 않으며, 판정 완료 후에도 승인 사례를 격리 목록과 다시 대조한다.

기존 합성 학습 32건에는 단순 거절·승인과 행위자 구분이 있지만, 명확한 타인 수신자에 대한 응답 보류와 복수 요청의 서로 다른 결정 범위가 빠져 있었다. 실제 발신 메시지만으로는 ‘답장을 보내지 않는 것이 맞음’의 정답을 얻기 어려우므로 별도 합성 보강 32건을 작성했다. 수신자 대조·복수 결정·확인 질문과 보류·최신 결정 유지 각 8건이며, 주관 에이전트가 전체 문맥과 정답을 검토하고 실제 토크나이저로 최대 680토큰임을 확인했다. 검증용 보강 8건은 학습 보강 본문을 보기 전에 독립적으로 작성·동결했다. 기존 교정본과 합치면 합성 학습 64건·검증 16건이며 실제 대화 수에는 포함하지 않는다. 아직 이 자료로 재학습하지 않았다.

별도 에이전트가 검증 보강 8건을 재검토해, 1건의 정답이 기존 배포 허용 대상의 범위를 빠뜨린 점을 발견했다. 원본 동결본은 보존하고 대상 범위를 유지하는 정답으로 revision 2를 만들었으며 8건 모두 재검토를 통과했다. 최초 작성은 학습 보강 본문을 보기 전, 이 교정은 학습 보강 검토 후라는 순서도 구분해 기록했다. 최종 평가 본문·출력은 교정에 사용하지 않았다.

의미 검토 과정에서 Slack 접속 토큰 표기, 한국어 암호 값, 회의 전화 PIN, 값 뒤에 붙는 자격증명 라벨 등 초기 패턴 검사가 놓친 사례를 발견했다. 발견한 원천 키를 먼저 격리하고 실제 값 없는 합성 회귀 사례로 검사를 보완했다. 기존 격리 보고서와 해시는 보존하며 새 버전으로 전체 승인 자료를 재검사한다. 패턴 검사는 완전한 비밀정보 탐지 보장이 아니므로 개별 의미 검토를 대체하지 않는다. 검토에서 발견한 계좌·생년월일 등의 금융신원 제출 원천도 별도 사유로 격리한다. 원문을 일부 가려 같은 승인 해시로 학습시키지 않는다.

내 계정으로 표시된 Slack 채널 가입·이름 변경·연동 추가 알림도 직접 작성한 대화 답장은 아니어서 제외했다. 수신자 이름이 운영 입력에 없거나, 달력·이동 상황·첨부 내용·오프라인 논의를 알아야 재현할 수 있는 답장은 보류한다. 반대로 문맥에 이미 있는 내 거절·결정을 유지하는 답장, 상대의 요청을 확인하는 질문, 확인 완료를 주장하지 않는 후속 확인 의사는 개별 근거에 따라 승인한다. 원래 대화에 존재한다는 사실과 현재 입력으로 추천해도 적절하다는 판단을 구분한다.

학습 후보 350건의 의미 검토는 승인 88·보류 186·제외 76건으로 완료했다. 승인 사례는 카카오톡 83·텔레그램 4·Slack 1건이며, 행동 유형은 인사·확인·격려 47, 확인 질문 11, 기존 결정·거절 유지 7, 후속 행동 의사 18, 문맥으로 뒷받침되는 정보 5건이다. 이는 사용자가 위임한 에이전트 검토(`agent_delegated`)이며 사람이 직접 검토했다고 기록하지 않는다. 최종 원천 격리·분할·중복 대조를 통과한 수로 학습 manifest를 확정하며, 이 시점의 승인 수를 학습 완료 수로 표시하지 않는다.

독립 실제 평가의 초기 60건에서 38건이 입장 기준을 통과해, 사전에 고정한 예비 36건의 조건부 검토를 시작했다. 고정 순서에서 10건을 추가해 목표 48건(카카오톡 44·Slack 4, 처음 보는 10개 방)을 확보했다. 이 중 입력이 2K를 넘는 것은 26건이며 최대 입력은 3,824토큰이다. 개별 품질 판정은 총 82건이고, 제외 34건은 자격증명 문맥 29건과 서비스 알림·빈 최신 본문 5건이다. 나머지 예비 사례를 성능에 따라 골라 넣지 않는다. 모델 출력 생성 전 최종 격리·중복 대조와 문맥별 평가 기준을 함께 동결한다. 기본 모델 대비 기존 적용 기준을 유지하며, 이전 미적용 어댑터와의 비교는 데이터 확대 효과를 살피는 별도 참고 결과로 보고한다.

새 검증은 초기 48건과 같은 예약 방에서 순서를 미리 고정한 추가 56건을 모두 검토했다. 총 104건 중 승인 30·보류 38·제외 36건이며 승인 사례는 모두 카카오톡이다. 실제 학습 정답의 최대 길이는 41토큰, 검증 정답은 63토큰이다. 합성 보강과 합친 예정 구성은 학습 152건(실제 88 + 합성 64), 검증 46건(실제 30 + 합성 16)이다. 이전 검증 12건을 이 수에 추가하거나 새 사례라고 재사용하지 않는다.

후보 선택은 학습 출력이 나오기 전에 별도로 고정한다. 2회 학습 중 반 회차마다 저장하는 4개 후보를 이미 관찰된 개발용 24건으로 비교하고, 명확한 의미 실패 수 → 의미 불확실 수 → 평균 유용성 → 평균 말투 → 실제 저장 가중치의 검증 손실 순으로 하나를 고른다. 기본 모델도 같은 개발 입력으로 비교하지만 후보 선택 대상은 4개 학습 가중치뿐이다. 사례별로 다른 후보를 고르지 않으며, 검증 손실만 가장 낮은 후보는 별도로 기록한다. 최종 실제 48건·합성 48건의 결과를 후보 선택에 사용하지 않는다.

설치된 MLX 학습기의 검증 손실 기록은 해당 반복의 업데이트 **전**, 체크포인트 저장은 업데이트 **후**다. 따라서 반복 번호만 같다고 손실을 저장 가중치에 연결하면 한 번의 업데이트 차이가 생긴다. 저장된 4개 가중치를 직접 불러 전체 검증 자료로 다시 측정한 손실을 사용한다. 학습 도중 5회와 저장 가중치 재평가 4회를 합친 검증 비용도 실행 시간 예산에 포함한다.

최종 원천 격리 목록은 49개 메시지 키다. 동결된 학습·검증·평가 검토 대상 550건을 재검사했으며, 승인된 학습·검증 118건과 최종 평가 48건에 격리 원천은 없었다. 실제 대화의 학습/검증/평가 사이 8,304개 쌍의 원천 키·정규화 본문·긴 본문의 유사도 검사도 통과했다. 이 검사는 의미가 같은 모든 바꿔 쓰기를 탐지한다는 보장은 아니다. 최종 실제 평가의 본문은 주관 및 학습 검토 에이전트에게 공개하지 않는다.

후속 학습 주기도 이번 검토를 재사용할 수 있도록 전역 검토 장부와 분할 예약을 병합했다. 기존 242개 판정과 원천·구간 예약을 보존하고, 달라진 입력은 정확한 검토 해시가 일치할 때만 승인 판정을 재사용한다. 새 검증·평가 방 21개와 그 안의 후보 496개는 사용 여부와 관계없이 예약했다. 민감 원천 목록은 필수 정책 해시로 연결하여 파일 누락·불일치 시 학습을 중단한다. 일일 스케줄의 플랫폼·2K 조건·수동 적용 방식은 유지한다.

민감 원천 검사 모듈이 배포 파일 목록에서 빠져 있던 문제도 보완했다. 실제 배포 번들을 만든 뒤 저장소 소스에 의존하지 않는 격리 Python 환경에서 학습 모듈을 불러오는 검사를 추가했고, 제품 통합 검사 1개/350개 assertion이 통과했다. 이 검사는 설치 증거와 구분하며, 최신 모듈의 운영 설치는 학습 프로세스와 충돌하지 않는 시점에 별도로 확인한다.

이번 비교는 실제 학습 22→88건과 합성 학습 32→64건의 확대, 합성 정답 교정 및 후보 선택 보완을 함께 적용한다. 결과가 좋아져도 메시지 양 증가 하나만의 인과 효과로 해석하지 않는다. 실제 학습량 확대는 4배지만, 확보한 메시지 44,382건 전부를 학습 정답으로 사용했다는 뜻도 아니다.

첫 확장 실행 `expanded-training-session-v1`은 학습·검증 업데이트 전에 종료됐다. 자식 실행 1.613초, 최대 RSS 약 5.19GiB, swap 추가 증가 0이었으며 완료 가중치는 없다. 설치된 MLX 로더가 존재하지만 비어 있는 테스트 분할 파일의 첫 행을 읽어 `IndexError`를 낸 것이 원인이다. 최종 평가를 학습 프로세스에 제공하지 않는 정책은 유지하고, 사용하지 않는 빈 분할 파일을 생성하지 않는 호환성 수정을 적용한다. 실패 계획·자원 기록은 보존하고 수정 후 별도 계획으로 재실행한다.

수정 검증 61개가 통과했다. 실제 설치된 MLX 로더로 빈 파일 오류를 재현하고, 수정된 학습 준비 경로에서 테스트 분할 0건과 검증 전용 평가가 모두 정상 로드됨을 확인했다. 각 저장 가중치의 검증 손실·가중치 SHA·검증 자료 해시·자원 기록을 완료 즉시 보존하고, 뒤 후보의 평가가 실패해도 앞선 결과가 남는 회귀 검증도 추가했다. 검토용 메모리 프로세스 4개를 정상 종료하여 약 2.04GiB를 해제했으며, 최종 실제 48건만 원본과 일치함을 독립 검증한 메모리 서비스에 유지한다.

재실행 `expanded-training-session-v2`의 계획 해시는 `aadeab3dbea2f9080016c1076a2fb5a0fcecd37f48863986068b6c19bf778302`다. 이전 실행과 비교해 출력 경로 및 위 호환성·검증 기록을 담당하는 모듈 해시만 바뀌었다. 실제 88/30건·합성 64/16건, 전체 304회 업데이트와 76회 간격 저장, 학습·검증 길이, 자원 한도, 원천·분할·입력 해시는 동일하다. 승인된 53개 방의 원천 3,175건을 다시 확인했고 새로운 최종 평가 방은 재구성 요청에 포함하지 않았다.


### 확장 재실행의 자원 중단과 진단

`expanded-training-session-v2`는 초기 검증 46건을 loss 2.855/219.973초에 완료했다. 76회차 직전 검증은 loss 2.553/226.390초였고, 76회 가중치 파일을 저장했다. 그러나 마지막 로그 90회 이후, 1,396.677초 시점에 시스템 swap 증가 4.167GiB가 4GiB 한도를 넘어 중단됐다. 최대 프로세스 RSS는 약 19.56GiB, MLX peak는 22.959GB였다. 학습 도중의 2.553은 업데이트 전 가중치의 손실이며 저장된 76회 가중치를 재측정한 결과가 아니다. 304회 학습·4개 후보 평가·독립 품질 비교는 완료되지 않았다.

실패 실행과 76회 체크포인트를 보존하고 데몬·암호화 저장소·스키마 7의 준비 상태를 확인했다. 기존 추천 모델을 유지한다. 이전 성공 실행의 최대 RSS 약 26.92GiB 및 MLX peak 22.968GB와 비교하면 이번 관측 peak가 더 크지는 않다. 이전의 시작 swap은 약 4.364GB, 이번은 약 1.428GB였으므로 시스템 전체 증가량만으로 학습의 실제 물리 메모리 부족을 확정하지 않는다.

설치된 학습기는 각 단계의 allocator cache를 이미 정리하지만, 입력 길이별 컴파일 결과는 별도로 관리한다. 원인 후보와 실험 기록은 `debug_notes.md`에 남긴다. 우선 전용 학습 프로세스에서만 컴파일을 끄는 설정을 추가해, 동일 계산의 수치·속도·자원을 비교한다. 학습 사례·순서·길이·학습률·LoRA 범위와 자원 한도를 동시에 바꾸지 않는다. 이 단계의 CPU 수치 일치는 전체 학습 완주나 원인 확정의 증거가 아니다.

후속 평가 준비에서는 합성 사례를 포함한 실제 사용 자료 전체의 입력 문맥도 대조했다. 학습 152건·검증 46건의 예제 해시 198개가 모두 동결 manifest와 일치했다. 시스템 지침·공통 출력 지시·정답을 제외한 입력 문맥으로 학습/검증/최종 평가 사이 26,000쌍과 실제/합성 최종 평가 사이 참고 비교 2,304쌍을 검사했고, 정확 중복·긴 문맥 유사·긴 발언 공유·전체 입력 동일 신호는 0이었다. 기존 실제 대화의 문맥+정답 비교 8,304쌍은 별도 증거로 보존한다. 최종 평가 사례·루브릭·적용 기준을 바꾸거나 출력에 따라 표본을 다시 고르지 않았다.

실제 9B 모델로 입력 길이만 다른 합성 자료 49개를 만든 뒤, 같은 순서의 56회 업데이트를 컴파일 기본/해제 조건에서 각각 실행했다. 기본 조건은 600초 제한 안에 36회를 완료했고, 해제 조건은 583.218초에 56회를 모두 완료했다. 같은 첫 36회의 시간은 587.308→363.468초로 약 1.62배 빨랐다. 최대 RSS는 각각 약 23.60/6.81GiB, 시작 대비 최대 swap 증가는 1.50/0GiB였다. 실제 모델의 같은 단계 손실 차이는 최대 약 0.009로, 비트 단위 동일 결과는 아니었다. 작은 모델의 손실·기울기·업데이트 수치 검증과 실제 모델의 관측 결과를 구분한다.

진단은 순차 실행이며 시작 swap과 여유 메모리가 달랐다. 진단 시작의 여유 메모리도 실패한 v2보다 약 14.2GB 많았으므로, 메모리 문제의 원인이 컴파일 하나였다고 확정하지 않는다. 진단의 새 입력 길이 비율은 전체 304회 학습보다 높아 속도 차이를 그대로 전체 시간에 적용하지 않는다. 데이터·학습률·학습 횟수·자원 한도를 유지한 채 전용 학습 프로세스의 컴파일만 끄는 재시도를 준비한다. 설정 기본값과 운영 추론은 유지한다.

### 사용자 방향 수정: 4K 데이터 확대 후 실제 메모리 검증

사용자는 기존 가중 학습을 멈추고 **4K 기준 데이터 확보·검수 → 확대된 실제 데이터로 메모리 가능 여부 확인 → 학습** 순서로 다시 진행하도록 지시했다. 해당 실행의 컨트롤러에 정상 중단 신호를 보내 자식 학습 프로세스 전체가 종료되고 메신저 데몬·암호화 저장소·스키마 7이 준비 상태로 돌아왔음을 확인했다. 중단 자원 기록은 `training_cancelled`, 실행 1,188.514초, 최대 RSS 약 6.87GiB, swap 추가 증가 0이다. 첫 76회 저장본과 원래 실패·중단 영수증을 보존하며, 이를 자원 실패나 완료된 품질 실험으로 취급하지 않는다. 가중 실험 재시작과 해당 실험의 개발 비교는 진행하지 않는다.

새 작업은 다음 순서로 진행한다.

1. 이미 확보한 기록에서 전체 학습 예제 4,096토큰 이내, 운영 입력 3,904토큰 이내의 후보를 다시 정리한다. 기존의 정답 65토큰 상한을 자동으로 적용하지 않고, 실제 정답 길이 65 이하·66–128·129–192·192 초과를 구분한다. 문맥이나 정답을 잘라 수량을 맞추지 않는다.
2. 기존 평가·검증 예약과 원천 격리를 유지하고 더 많은 실제 대화를 검수한다. 우선 실제 승인 300개 이상 확보 가능성을 확인하되 품질 기준을 낮춰 수량을 채우지 않는다. 방·길이·답장 기능의 분포와 반복 구간을 확인하고, 3,840–4,096토큰 경계에 가까운 실제 사례도 포함해 검토한다. 이전 검토는 원문·입력·정답·검토 해시가 그대로일 때만 재사용한다.
3. 확정된 실제 학습 자료에서 대표 길이, 가장 긴 문맥, 가장 긴 정답과 주요 조합을 골라 메모리 검증을 한다. 모델·학습률·LoRA·마스킹·전체 문맥을 실제 학습과 맞추고, 한 프로세스에서 여러 길이를 반복 처리해 최대 사용량과 누적 증가를 측정한다. 시작 전 충분한 메모리 여유와 안정 상태를 확인한다. 앞선 합성 4K 실패는 시작 자원 조건이 달랐으므로 4K 자체의 불가능 근거로 삼지 않는다.
4. 실제 데이터의 메모리 검증이 통과하면 확정된 데이터 수와 실측 속도에 맞춰 전체 학습 시간·저장 간격·자원 한도를 정해 학습한다. 중간 실행 결과에 맞춰 한도를 완화하지 않으며, 학습 완료 후 추천 품질을 비교해 적용 여부를 결정한다. 봉인된 최종 96건은 데이터 선택이나 메모리 검증에 사용하지 않는다.

4K는 예제의 최대 길이이고 데이터 수는 별개다. 큰 데이터셋은 주로 전체 학습 시간을 늘리며, 최대 길이·정답 길이·배치·실행 방식은 순간 메모리에 영향을 준다. 이번에는 이 둘을 실제 확대 자료로 함께 확인한다. 실측한 최대 예제가 4K 경계에 못 미치면 그 범위의 성공으로만 기록한다.


4K 재구성에서는 평가·검증 예약을 제외한 123개 방의 동결 원천 11,742행과 후보 3,086건을 모두 원본·입력·정답·원천 해시로 대조했다. 불일치와 원천·구간 경계 위반은 없었다. 토크나이저 반환 형식 오류로 첫 준비 실행을 중단한 뒤 같은 범위를 다시 대조했고, 수정 실행에서 종료 토큰과 전체 prefix 일치까지 확인했다. 준비 증거는 `fourk-dataset-expansion-v1/preparation-v2/preparation-proof.json`에 보존한다.

전체 후보는 새 의미 검수 2,306건, 민감 정보 문맥 제외 410건, 정확히 같은 기존 판정 재사용 370건으로 나뉜다. 재사용 판정 자체가 최종 학습 승인은 아니며, 이후 보류로 바뀐 사례와 중복·입장 조건을 함께 적용한다. 새 검사에서 확인한 민감 원천 51개를 기존 95개에 더한 146개 목록으로 이 준비 자료를 검사했다. 첫 512건 중 새 검수 235건은 Sol 109건·Luna 126건으로 겹치지 않게 배분했다. 나머지 156건은 기존 판정 재사용, 121건은 민감 문맥 제외다. 민감 문맥을 통과한 새 검수 후보의 최대 전체 길이는 3,904토큰, 최대 전체 정답 길이는 183토큰이며, 두 최대값이 같은 사례라는 뜻은 아니다. 실제 학습과 확대 자료의 메모리 시험은 아직 시작하지 않았다.


첫 복잡 사례 109개의 원판정은 승인 30·보류 74·제외 5개로 완료했다. 주관 에이전트는 승인된 최대 입력과 최대 정답 사례를 표본 점검했다. 전체 3,904토큰 사례는 앞선 요청에 근거한 후속 문의 의사로 재확인했고, 최대 정답 사례와 비슷한 4개는 의미상 근거와 별개로 운영 지침의 ‘짧은 답장 한두 문장’에 맞지 않아 최종 입장에서 보류했다. 원래 판정은 보존하고 `root-qa-admission-overlay-v1.json`으로 5개 보류를 추가했다. 정답 길이 자체를 일괄 제외하거나 원문 일부만 잘라 승인한 것이 아니다. 앞으로의 학습 자료와 메모리 시험은 이 입장 판정까지 적용한 실제 최대 길이를 사용한다.

추가 의미 검수에서 발견한 민감 원천까지 포함한 현재 목록은 151개다. 모든 3,086개 후보의 원천 키와 연결된 후보 목록을 따로 저장해, 추가로 발견한 원천은 대화를 다시 수집하지 않고 영향 범위를 계산한다. 이 기준의 후보 상태는 새 의미 검수 2,274·민감 문맥 제외 442·기존 판정 재사용 370개다. 첫 묶음과 겹치지 않는 다음 512개는 데이터 담당 182·Sol 202·Luna 128개로 배분했다. 초기 Luna의 8개 판정은 그대로 두고 남은 첫 묶음 115개는 Sol이 이어서 검토한다. 에이전트 검수라는 출처를 명시하며 사람 검수로 기록하지 않는다. 학습·최종 평가·운영 적용은 아직 시작하지 않았다.


사용자가 매일 오전 4시 학습 일정을 삭제하도록 명시하여 `page.boaz.inboxd.learning`을 unload하고 설치된 LaunchAgent plist를 삭제했다. 기존 일시 정지·재개 계획은 이 지시로 폐기한다. 일정 삭제 영수증은 `scheduler-deleted-by-user-v1.json`이다. 앞으로는 학습 필요성을 판단한 뒤 필요한 경우에만 실행하는 방향이며, 판단 로직은 아직 추가하지 않았다. 과거 절의 04:00 실행 기록은 당시 상태를 설명하는 이력이다. 이번 명시적 4K 학습 요청은 별도로 계속한다.

## 17. 모델 선택과 4K 학습 메모리 원인 분석

2026-10-04 사용자가 현재 모델의 적합성과 근본적인 메모리 원인을 다시 분석하도록 요청했다. Sol은 설치된 MLX 0.32.2·mlx-lm 0.31.3의 학습 경로와 작은 합성 CPU 계산을, Luna는 공식 모델 설정·카드를 확인했고 주관 에이전트가 실측 기록·현재 코드와 대조했다. 실제 모델을 새로 로드하거나 GPU 학습을 실행하지 않았다.

### 관측으로 확인한 범위

현재 모델은 Qwen3.5-9B 4bit이고 batch 1, 마지막 4개 레이어의 LoRA를 학습한다. 4bit는 주로 기본 가중치의 저장 비용을 줄이며, 학습 중간값까지 4bit로 만드는 설정이 아니다. recurrence state는 float32다. 동일한 어댑터 구성에서 확인한 학습 파라미터는 2,704,896개로 float32 가중치 자체는 약 10.8MB다. 기울기와 Adam 상태를 더해도 이 고정 파라미터 저장량만으로 수십 GB를 설명하지 못한다. 어댑터 관련 행렬 연산의 중간값은 별도다.

실제 경고 허용 진단 한 번의 관측은 다음과 같다. GB는 10진 단위이며 MLX 값은 해당 시점까지의 누적 최대 활성 메모리다. 시스템 전체 wired 메모리나 프로세스 RSS와 다른 지표다.

| 완료 지점 | MLX 최대 활성 메모리 |
|---|---:|
| 첫 고정 prefix 계산 | 5.765GB |
| 2,305 패딩 토큰의 첫 업데이트 | 25.081GB |
| 2,465 토큰의 두 번째 업데이트 | 26.494GB |
| 2,753 토큰의 세 번째 업데이트 | 28.994GB |
| 3,137 토큰의 네 번째 업데이트 | 32.328GB |

다섯 번째 긴 사례에서는 OS 압력 critical로 중단됐다. 전체 535개를 동시에 계산하는 설정이 아니며, 데이터셋 수보다 한 예제의 토큰 길이에 따라 커지는 학습 중간값이 우선 원인이다. 정답 위치 최대 66개만 출력층에 보내므로 4K 전체 위치의 거대한 vocabulary logits를 만드는 문제는 이미 피하고 있다. 고정 prefix를 gradient 밖으로 분리해도 첫 3회의 peak는 같았다. 캐시 제한·실행 순서 조정의 개선은 충분하지 않았다.

### 가장 유력한 병목: 반복 상태의 학습 경로

Qwen3.5-9B는 32개 레이어 중 24개가 GatedDeltaNet이고 8개가 일반 attention인 혼합 구조다. 마지막 4개 학습 레이어에도 recurrence 3개가 있다. 설치 코드의 `use_kernel=not self.training`에 따라 추론은 전용 Metal kernel을 사용할 수 있지만 학습은 토큰별 일반 연산 경로를 사용한다. 이 경로는 상태 크기의 곱셈·덧셈 중간값을 만들고 자동 미분한다. [공식 구조](https://huggingface.co/Qwen/Qwen3.5-9B), [mlx-lm 학습 경로](https://github.com/ml-explore/mlx-lm/blob/v0.31.3/mlx_lm/models/qwen3_5.py#L167-L178), [반복 연산](https://github.com/ml-explore/mlx-lm/blob/v0.31.3/mlx_lm/models/gated_delta.py#L126-L167).

batch 1에서 상태 하나는 `32 × 128 × 128 × float32 = 2MiB`다. 토큰별 상태 하나씩을 4,096개 보존한다고 가정하면 레이어 하나에서만 8GiB 규모다. 이는 크기를 이해하기 위한 가정이며 실제 GPU 할당 내역이 아니다. 실제로 어떤 상태·임시값이 동시에 몇 개 살아 있는지는 아직 계측하지 않았다. 관측 peak는 완료한 구간에서 토큰당 약 8.7MB 증가했고 prefix 분리는 이를 줄이지 못했다. 이 관측과 소스 구조를 합치면 학습 대상 suffix의 recurrence 미분·재계산 경로가 가장 유력하지만, 메모리 전부를 특정 텐서 하나의 탓으로 확정하지 않는다.

### Checkpoint와 컴파일에 대한 확인·정정

현재 32토큰 checkpoint는 재계산 단위를 정한다. 전체 backward가 항상 32토큰분의 메모리만 유지하도록 실행 순서를 강제하는 것은 아니다. MLX checkpoint는 backward에서 원 함수를 다시 미분하며, 작은 CPU 대조에서 128토큰 step 호출 수가 checkpoint 없음 128회, chunk32 256회, 바깥 checkpoint를 추가하면 384회였다. 따라서 checkpoint가 전혀 작동하지 않는다는 설명은 틀리다. [checkpoint 구현](https://github.com/ml-explore/mlx/blob/v0.32.2/mlx/transforms.cpp#L1102-L1112), [CustomTransforms VJP](https://github.com/ml-explore/mlx/blob/v0.32.2/mlx/primitives.cpp#L1745-L1772).

`mx.disable_compile()`은 내부 step을 포함해 컴파일을 전역으로 끈다. 그러나 미분 중 tracer 입력이 들어오면 compile wrapper 자체가 원 함수로 돌아가는 경로가 있다. 내부 step compile on/off CPU 대조는 모두 primitive 20,043개·step 호출 384회였고 loss와 전체 5개 gradient 배열의 hash도 같았다. 단순히 내부 step 컴파일을 켜면 해결된다는 근거는 없다. [tracer fallback](https://github.com/ml-explore/mlx/blob/v0.32.2/mlx/compile.cpp#L1137-L1141).

미분 계산 전체를 compile하면 작은 CPU 그래프는 14,132개로 줄었지만 CPU RSS 증가분은 약 33.2→45.0MB였고 JIT 비용도 생겼다. GPU peak 개선을 검증한 결과가 아니다. 앞선 실제 9B 가변 길이 실험에서는 전체 컴파일 해제가 RSS·시간을 줄였으므로, 전역 컴파일을 다시 켜는 것을 바로 해결책으로 채택하지 않는다. 향후 구현을 개선한다면 학습용 recurrence의 미분 연산 결합과 chunk별 backward 실행·해제 순서를 직접 검증해야 한다.

CPU 계산은 상태 512바이트의 합성 예제로 실제 9B보다 훨씬 작다. 그래프 크기나 CPU RSS를 GPU peak 절감량으로 환산하지 않는다. 원본 runtime과 설치 라이브러리는 수정하지 않았다. 실행 코드·결과는 비공개 작업 디렉터리 `expansion-20261003/model-memory-analysis-v1/`에 보존했다. 결과 파일 `inboxd_recurrence_memory_conclusion_cpu_v1.json`의 SHA256은 `84c3e217f4cc118cd1fadaf68fe180372db3f90dfa89efef3f4f6b3ac68720c1`이다.

## 18. 사용자 요청에 따른 메모리 구현 수정과 학습 재개

사용자가 메모리 문제부터 해결하고 학습을 끝까지 진행하도록 지시하여 작업을 재개했다. 앞 절의 중단은 과거 상태다. 데이터 535/46건, 전체 문맥·정답 토큰, 마지막 4개 LoRA 층, 학습률, 정상 메모리 압력 조건과 최종 품질 기준은 유지한다.

### 병목 위치와 실패한 구현

chunk별 custom VJP와 독립 leaf 복사 방식은 작은 CPU 모델에서 원래 기울기와 일치했지만 실제 9B 첫 업데이트 중 압력 경고로 중단됐다. 별도 계측 실행에서는 고정 prefix 완료 시 MLX 활성 메모리 약 5.08GB, 최대 5.71GB였고 학습 suffix forward 뒤 활성 메모리가 5.84→8.51→11.18GB로 증가했다. backward 입력 평가 과정에서 13.72GB에 도달하여 사전에 정한 12GiB 진단 한도로 중단했다. 이 진단의 OS 압력 표본은 모두 정상이며 추가 스왑은 0이었다. prefix보다 suffix의 미분 그래프·중간값 평가 경로에 증가가 집중됐다는 근거이며 특정 텐서 하나의 할당 내역을 확정한 것은 아니다. 두 실행 모두 데몬과 암호화 스키마 7 복구를 확인했다.

### 병렬 청크 계산과 수치 검증

[Hugging Face의 Qwen3.5 청크 알고리즘](https://github.com/huggingface/transformers/blob/v5.13.0/src/transformers/models/qwen3_5/modeling_qwen3_5.py#L227-L300)을 MLX의 미분 가능한 행렬 연산으로 옮겼다. 토큰별 큰 상태 계산 대신 청크 내부의 작은 행렬과 청크 간 상태를 사용하며, 입력 생략·truncated BPTT·gradient 차단은 하지 않는다. 학습 프로세스에서만 교체하며 추론은 설치된 원래 함수를 사용한다. 소스 SHA256은 `7633639a869c4b76cee80d0c3372b3ac496bbd2e010613f8d47540935c39adda`다.

초기 C32·16·8·4 검사는 모두 기존 통합 RMS 기준에 실패했다. 원소별 절대·상대 오차 검사를 통과해도, 거의 0인 기울기의 RMS를 절대 허용 오차로 나눈 뒤 별도의 작은 기준을 적용해 실효 절대 한도가 `2e-5 × 2e-4 = 4e-9`가 됐다. 계산 순서를 바꾼 float32 결과를 검사하기에 의도한 절대 허용 오차보다 5,000배 엄격한 결합이었다. 기존 실패를 통과로 고치지 않고 별도 프로토콜을 동결했다. 원소별 atol/rtol·finite·shape·dtype 조건은 그대로 유지하고 RMS를 `RMS(차이)/(atol + rtol × RMS(기준값)) ≤ 1`로 일관되게 수정했다. 이 RMS는 원소별 조건에서 따라오는 보조 지표이며 독립적으로 더 강한 검사가 아니다. 기존 결과를 본 뒤 검사식을 수정했다는 점도 기록한다.

C16을 고정해 새 프로토콜로 재실행한 결과, 작은 32층 모델의 전체 학습 기울기 62개, Adam 연속 2회 업데이트·상태·중간 검증을 모두 통과했다. 이전 C16과 1,356개 텐서의 수치·원소별 판정이 같았으며 변경된 것은 RMS 판정식이다. 독립 검토 봉인은 `6f9bff5f19fe7ed801b54a29dd33af431034670f15aa672c55b025d4de3f1803`이다. 별도의 고정밀 계산·유한차분 검증과 실제 6개 길이·18회 자원 시험을 이어서 수행하며, 이 CPU 결과를 실제 메모리 또는 답장 품질 개선으로 간주하지 않는다.

### C16 실제 자원 시험 통과

별도 NumPy64 직접 순환·삼각행렬 풀이·수작업 역미분·두 간격의 중심 유한차분 대조 3건을 통과했다. 실제 9B/동일 6개 사례의 18회 업데이트도 **261.3초에 모두 완료**했다. OS 압력 표본은 전부 정상(1), 추가 스왑 0, 최대 MLX 활성 메모리 30.05GB였으며 데몬·암호화 스키마 7 복구를 확인했다. 같은 세 번째 입력의 최대 활성 메모리는 기존 BFS4 약 28.99GB에서 18.33GB로 감소했다. 각 업데이트 후 활성 메모리는 약 5.08GB로 내려왔고 반복 중 최대치 누적 증가는 관측되지 않았다. GPU 메모리와 별개인 process RSS 최대는 5.53GB였다.

다음 개선 실험은 일반 인사량을 더 늘리기보다 같은 상황의 화자·최신 결정·동의 범위만 바꾼 짝 사례, 올바른 확인 질문과 불필요한 응답 포기의 구분, 거절 보존에 우선순위를 두는 것이 타당하다. 기준을 바꾸지 않은 별도 개발 비교로 효과를 확인하고 새로운 독립 최종 자료를 확보해야 한다. 현재 9B가 최선이라는 모델 간 비교 근거도 아직 없다. 일반 attention 구조의 Qwen3-4B-Instruct-2507 4bit 후보는 준비했지만 품질 비교·학습은 수행하지 않았으며, 이번 성공은 기존 9B의 학습 메모리 문제를 해결한 결과다.

### 18.6 소스 통합·검증·정리 완료

최종 판정과 요약이 확정된 후에만 평가 중 고정했던 소스를 변경했다. 변경 전 파일과 해시는 private `runtime-integration-draft-v1/preintegration-source-snapshot/`에 보존한다. 검증된 병렬 recurrence·고정 prefix helper는 실제 학습에 사용한 바이트와 같고, 새 `qwen35-training-runtime-v5`의 명시적 `parallel_chunk16` 선택 경로로 연결했다. 기존 `legacy` 기본값은 유지하며 새 경로는 compile disabled, Qwen3.5 32층·앞 28층 고정·뒤 4층 학습 구성을 요구한다. 추론은 원래 함수를 사용하고 학습 성공·오류·취소 때 프로세스 내부 hook을 복구한다.

`personalization.py` CLI·학습·저장본 재평가에 backend 선택을 전달하고 실제 설정·소스 SHA·MLX 의존성 버전·결합 fingerprint를 manifest와 receipt에 남긴다. 제품 패키징 목록에 두 helper를 추가했다. config 파일을 확실히 닫도록 수정했고 관련 ResourceWarning도 사라졌다. 실제 학습과 최종 평가는 이전 봉인 소스에서 실행된 결과이며, 새 통합 코드를 사용한 실제 9B 전체 학습을 추가로 실행했다고 주장하지 않는다.

관련 검사는 총 **71개 통과, skip 0**이다: backend 연결·복구 8, 기존 수치/loss/masking/compile 5, 개인화 21, 학습 파이프라인 22, 확장 학습 14, 새 실제 CPU 통합 1. 새 통합 검사는 작은 합성 Qwen3.5 32층 모델에서 새 installer→학습 진입→고정 prefix→전체 62개 기울기→Adam 2회·중간 검증을 통과시켰다. 기존 legacy와 loss·모든 기울기·전체 파라미터·optimizer state가 사전 고정 허용오차 안에서 일치하고 고정 파라미터와 hook 복원을 확인했다. 실제 메시지·모델 가중치·GPU는 사용하지 않았다. 허용오차를 이번 결과에 맞춰 바꾸지 않았다.

설치된 학습 모듈 네 개(`personalization.py`, `training_runtime.py`, `parallel_chunk.py`, `prefix_outside.py`)를 백업 후 갱신했고 소스 SHA 일치와 저장소 경로 없이 설치본만 사용하는 격리 import를 확인했다. 전체 제품 재빌드·추론 worker 변경·어댑터 활성화는 하지 않았다. 설치 영수증 SHA256은 `8b7813b736ba51bdbfb4b5a9fb667458427d15d3177453772200028eb50d0850`이다.

새 backend 옵션은 알고리즘 선택만 담당한다. 성공한 48GiB Mac 자원 조건에는 **C16·고정 prefix 분리 + 첫 MLX import 전 BFS 폭 4 + 20GiB 메모리 가이드라인 + 1GiB 캐시 + 캐시 정리 threshold 0 + gradient checkpoint + 정상 메모리 압력 감시**가 함께 포함됐다. 20GiB는 엄격한 할당 상한이 아니며 backend 옵션만으로 이 전체 정책이나 30GB 상한을 재현한다고 주장하지 않는다. 기존 전용 controller와 봉인된 실행 계획이 완전한 재현 근거다. 사용 방법·범위는 [개인화 실행 문서](../packages/reply-model/PERSONALIZATION.md)에 기록했다.

최종 검토용 임시 본문 디렉터리는 controller 종료와 함께 제거했다. 학습용·최종 실제 평가용 RAM owner 두 개도 정확한 PID와 실행 파일을 확인한 뒤 SIGTERM으로 정상 종료했고, 본문 미보존 종료 영수증을 확인했다. 추천 서비스는 기존 기본 모델로 복구됐으며 활성 어댑터는 없다. 매일 오전 4시 학습 일정은 삭제 상태를 유지한다. 학습 필요성 판단 로직은 이번에 구현한 것으로 표시하지 않는다.


### 18.7 2026-10-05 후보 검토 범위 정정과 저장 공간 정리

사용자가 3,000건 이상 확보했는데 학습량이 작은 이유를 물어 원본 메타데이터 장부를 다시 대조했다. `pool-ledger.json`에는 중복 없는 후보 3,086개가 있고, `admission-preflight-v2.json`에는 그 부분집합인 1,117개의 의미 판정이 있다. 기존 판정 재사용 370개와 신규 두 묶음 235+512개를 처리한 범위다. 결과는 승인 481·보류 603·제외 33개이며, 승인 후 형식·중복 문제 10개를 추가 보류하여 실제 학습 471개가 됐다. 여기에 합성 64개를 더해 학습한 것이 535개다.

나머지 1,969개는 이 완료된 의미 판정 장부 범위 밖이다. 민감 문맥 자동 제외와 미검토 후보 등을 따로 재집계해야 하므로 전부 학습 가능하거나 전부 품질 탈락한 것으로 표시하지 않는다. 원래 계획은 남은 묶음을 전체 후보 범위까지 추적하고 유용한 자료가 남았는데 승인 300개에서 멈추지 않는 것이었다. **실제로는 전체 후보의 의미 검토를 끝내기 전에 학습으로 넘어갔다.** 따라서 전체 후보 검토 완료로 해석한 진행 보고와, 확보 자료를 모두 활용한 뒤 데이터가 부족했다고 읽힐 수 있는 설명을 정정한다. 학습·최종 평가 자체의 완료 결과는 유지한다. 이번 메타데이터 대조만으로 당시 범위를 줄인 이유까지 확인한 것은 아니다.

이어서 사용자가 실험 후 불필요한 파일을 삭제해 저장 공간을 확보하라고 지시했다. 운영 프로세스의 열린 파일, 활성 어댑터 부재, 설치본과 빌드 산출물의 분리를 확인한 뒤 다음을 삭제했다.

- 이 저장소의 재생성 가능한 `target/` 빌드·테스트 산출물 전체.
- 사용하지 않은 `Qwen3-4B-Instruct-2507-4bit` 비교 모델과 원래 tokenizer 사본.
- 비활성 실험 어댑터·체크포인트 `.safetensors` 42개. 재학습 없이 해당 가중치를 다시 평가할 수는 없으며 삭제 전 경로·크기·SHA256을 보존했다.
- 실험 전 실행 파일 사본, 오래된 실패 제품 사본, 실험 Python bytecode 캐시.

운영 Qwen3.5-9B 모델·설치 제품·Python 실행 환경, 메시지 DB와 암호화 백업, 후보·의미 검토·최종 평가 기록, 소스·문서는 보존했다. 파일 정리는 휴지통 이동이 아닌 실제 삭제이며 다른 프로젝트의 진행 중인 빌드는 종료하지 않았다. 파일 크기 합산에는 hardlink 등 중복이 있을 수 있어 확보량은 파일 합계 대신 파일시스템 여유 공간 차이로 측정했다. **여유 공간은 약 3.72GiB→24.34GiB, 순증 약 20.63GiB**였다. 정리 후 추천 데몬·암호화 저장소 스키마 7의 ready 상태를 확인했고 잔여 학습 임시 디렉터리도 없었다.

삭제 계획·개별 삭제 로그·가중치 해시·완료 기록은 private `learning/cleanup-20261005/`에 남겼다. 앞 절의 가중치·모델·과거 실행 파일 보존 기록은 실험 종료 당시의 이력이며, 실제 보관 상태는 이번 삭제 기록이 우선한다. 학습을 추가로 시작하거나 새 어댑터를 적용하지 않았다.
